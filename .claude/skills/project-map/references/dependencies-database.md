# Зависимости: База данных и настройки

«Меняешь X — проверь Y». Часть общего раздела зависимостей карты проекта;
соседние части перечислены в `SKILL.md`.

- **⚡ Пишешь НОВУЮ функцию в `database/history.py` (2026-07-27)** → четыре правила, все из-за того, что соединение теперь ОДНО на весь процесс. (1) `conn = _get_connection()` звать ТОЛЬКО внутри `with _lock` — как все 74 существующие функции; вне замка два потока полезут в одно соединение одновременно. (2) `conn.close()` НЕ писать: он ничего не делает (пустой `close()` у `_LoggingConnection` — заслон от убийства общего соединения), и читатель кода будет обманут. (3) Пишешь в базу — обязательно `conn.commit()`, как и раньше: транзакция теперь живёт в общем соединении, и без commit её содержимое уедет в чужой commit следующей функции. (4) Ловишь исключение ВНУТРИ `with _lock` и не выпускаешь его наружу (как `subscribe_chat` с `sqlite3.IntegrityError`) — сделай `conn.rollback()` сам: откат в `_DbLock` срабатывает только на исключение, вылетевшее ИЗ блока замка.
- **⚡ Новый запрос в интернет (к модели, к сайту, к Telegram raw API)** → звать через `services.http.session()` (в gemini.py/rag.py/scraper.py он импортирован как `_http`, то есть `_http().post(...)`), а НЕ через `requests.post/get` напрямую: прямой вызов заново платит TLS-«рукопожатие» 130–200 мс. `import requests` в файлах остаётся — из него берутся типы ошибок (`requests.exceptions.Timeout` и т.п.), обработка ошибок не меняется. ⚠️ В `services/http.py` НЕ включать повторы (`max_retries`): они умножатся на собственные повторы бота, и таймаут 60 с превратится в минуты.
- **Новая таблица БД** → добавить в `database/history.py::_create_schema` (с 2026-08-03 схема живёт там, а не прямо в `init_db`) И в `reset_db.py::USER_TABLES`. Число таблиц сверяет `preflight.py`. Копится со временем — не забыть чистку в `jobs/cleanup.py` и срок хранения в config.py (так заведены `knowledge_log`, `staff_log`, `proactive_log`, `join_log`).
- **🎮 Банк вопросов викторины `quiz_bank` (2026-08-05)** → четыре правила. (1) `options` лежит СТРОКОЙ JSON (sqlite списков не умеет), и разбор спрятан в `_row_to_question` / `add_quiz_question`: наружу всегда уходит готовый список. Разложишь `json.loads` по вызывающим — однажды забудешь в новом месте и получишь строку вместо вариантов ответа. (2) Битый JSON вариантов НЕ роняет выборку: `_row_to_question` вернёт None, строка молча пропускается, в лог идёт предупреждение. (3) `approved` — прямая семантика: 0 черновик, 1 в игре; викторина берёт ТОЛЬКО единицы. (4) Выбор идёт `ORDER BY asked_count, RANDOM()`, а счётчик растит `note_quiz_question_asked` — звать его ТОЛЬКО после удачной отправки опроса, иначе вопросы, не дошедшие до чата, тихо уедут в конец очереди и выпадут из игры. ⚠️ Вопросы живут В БАЗЕ, а не в файле, ровно по той же причине, по которой из репозитория убрали `knowledge_base_vectors.json`: файл, который бот переписывает сам, ломает обновление кода с GitHub.
- **👋 Журнал вступлений `join_log` (2026-08-04)** → по ДВЕ строки на новичка: `join` (вошёл) и исход — `ok` / `timeout` / `kick`. Отдельная таблица, а НЕ `moderation_log`, и это не случайность: вступления идут потоком и вытеснили бы муты из «Последних действий» панели /mod, где всего пять строк. Обратная сторона — кик не прошедшего пишется в ОБА журнала (в модерации он законная запись: человека выгнали из группы), поэтому `get_join_counts` и `get_moderation_counts` считают его каждая по-своему, и складывать их цифры нельзя. Время — `time.time()`, как в `moderation_log`, а не `CURRENT_TIMESTAMP`: обе таблицы читает одна и та же панель, и разнобой форматов пришлось бы разбирать в ней.
- **Новая графа в существующей таблице** → мало добавить её в `CREATE TABLE` (он выполняется только для НОВОЙ базы): у работающего бота таблица уже есть, и графа не появится. Нужна СТРОКА В `_COLUMN_MIGRATIONS` (кортеж рядом с `_create_schema`, 2026-08-03): прогоняется на каждом запуске, «колонка уже есть» отвечает `sqlite3.OperationalError` и глушится — так сделаны model_name, admin_name, username/first_name в user_dossier, has_voice и has_video. Одного CREATE мало ВСЕГДА, даже если графа с DEFAULT.
- **Персональные настройки участника (`user_settings`)** → ПУСТОЕ поле означает «работает общая настройка бота», а не ноль. Читать только через `is None`, НЕ через `or`: персональный ноль (например, лимит картинок 0 = запрет) иначе молча превратится в общую настройку. Менять колонки разрешено только из белого списка `_USER_SETTING_FIELDS` — имя колонки вклеивается в текст SQL, параметрами его не подставить.
- **Меняешь персональные настройки кодом (2026-07-20)** → ТОЛЬКО через `services.user_settings.set_field` / `clear`. Прямая запись в БД (`set_user_settings` из history.py) не обновит кэш в памяти, и бот будет жить со старым значением до перезапуска — а читает он всегда кэш. Читать — тоже через этот модуль (`get`, `thresholds_for`, `is_immune`, …), а не из БД: смысл кэша в том, что на горячем пути похода в базу нет.
- **Убрал `user_settings.load()` из main.py** → кэш подхватится «ленивым» первым обращением (страховка внутри `get`), но одна лишняя загрузка случится посреди обработки сообщения. Вызов при старте не убирать.
- **Новая настраиваемая фича** → дефолт в config.py, живое значение через get_setting/set_setting (settings хранит СТРОКИ: "1"/"0", числа приводить через int с фолбэком).
- **Трогаешь `init_db` (2026-08-03)** → он разложен на три шага и сам ничего не делает: `_create_schema` (таблицы и индексы), `_run_column_migrations` (графы, появившиеся позже базы), `_seed_once` (разовое наполнение новых таблиц из уже накопленных данных). ПОРЯДОК ОБЯЗАТЕЛЕН — миграция и засев работают по таблицам, которые создаёт первый шаг. Все три получают соединение ПАРАМЕТРОМ и зовутся изнутри `with _lock` из `init_db`: своего `_get_connection()` в них быть не должно. ⚠️ Новый засев писать ТОЛЬКО с условием «таблица пуста», как оба существующих: он выполняется на каждом запуске, и без условия будет заливать данные заново. У переноса `user_token_usage` это условие — ещё и причина, по которой `clear_user_token_usage` обнуляет графы UPDATE-ом, а не удаляет строки (иначе месячный сброс вернул бы старые числа при следующем запуске).
