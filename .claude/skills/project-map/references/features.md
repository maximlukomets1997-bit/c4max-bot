# Функции бота (проверено по коду)


### 2.1 Публичные команды
- `/start`, `/help` — справка (HTML, панельное сообщение).
- `/clear` — очистка контекста диалога пользователя; подтверждение самоудаляется через 7 сек, после чего в личке у персонала автоматически открывается /adm.
- `/subscribe`, `/unsubscribe` — подписка чата на рассылку новостей.
- `/imagine <описание>` — картинка через Nano Banana (gemini-*-image); лимит 3/день на юзера, админ — безлимит.
- `/rank` — «личное дело»: звание, статистика викторин, остаток лимита картинок, блок «🪪 Служба в гарнизоне» (стаж, сообщений в группах, статус «✅ Проверенный» / «⏳ испытательный срок» / «⚠️ взыскание» — antispam.trust_info), прогресс-бар.
- **Команды `/quiz` НЕТ** — `cmd_quiz` существует в quiz.py, но НЕ зарегистрирован в handlers/__init__.py. Викторина запускается только кнопкой.
- Неизвестная команда → молча удаляется, без ответа.
- В меню Telegram: start, help, imagine, rank, subscribe, clear (без unsubscribe). У админов в личке сверху добавлена /adm.

### 2.2 Админ-команды (только ADMIN_IDS; не-админу — молчаливое удаление команды)
- `/adm` — главная панель-хаб (единственная админ-команда в меню). Только в личке; в группе молча выходит.
- `/stats` — тонкая панель «💬 СТАТИСТИКА» (только личка): 3 строки — обмены «вопрос-ответ» за текущий месяц (из user_token_usage, обнуляется месячным сбросом — см. 2.5), подписчики на новости, архив группы за последние 10 дней; из кнопок только «⬅️ Админ-панель». Бывшая общая панель разделена 2026-07-05 на три: статистика, промпты (`send_prompts_panel`), модели/API (`send_api_panel`) — все три шлются через общий помощник `_send_panel_message` (нарезка >4000 симв., запасной путь без HTML). `get_bot_stats` больше НЕ считает: окна контекста, «сегодня» по диалогам, уникальных пользователей/чатов, «сегодня» по архиву.
- `/mod` — панель модерации (только личка).
- `/users` — панель «👥 Пользователи»: список всех, кого знает бот, и карточка участника (только личка, 2026-07-20). В меню Telegram НЕ добавлена — как /mod, /rag, /stats.
- `/rag` — панель базы знаний (только личка).
- `/unmute` — ТОЛЬКО В ГРУППЕ: ответить командой на сообщение нарушителя. В личке — подсказка.
- `/prompt_set`, `/prompt_add`, `/prompt_reset` — системный промпт (текстом или .txt через Reply).
- `/news_prompt_set`, `/news_prompt_reset` — промпт форматирования новостей.
- `/rag_prompt_set`, `/rag_prompt_reset` — «шапка»-инструкция RAG (текстом или .txt через Reply); reset возвращает ЗАВОДСКУЮ (не «пусто»), с подтверждением. Хранится в settings `rag_instruction`, дефолт `RAG_INSTRUCTION` (config.py). Показывается блоком в панели /prompt.
- `/proactive_prompt_set`, `/proactive_prompt_reset` — инструкция участия в разговоре (режим «Сам в разговор»); зеркала /rag_prompt_* (текстом или .txt через Reply; reset возвращает ЗАВОДСКУЮ, с подтверждением). Хранится в settings `proactive_instruction`, дефолт `PROACTIVE_INSTRUCTION` (config.py). Показывается блоком в панели /prompt.

В файл SYSTEM PROMPT идёт склейка с дополнениями /prompt_add — то, что реально уходит модели. Кнопка отвечает попапом «⏳ Отправляю файлы…» ДО отправки (у Telegram ~15 сек на ответ callback). Кнопка «⬅️ Назад к панели» после /prompt_* ведёт СЮДА (callback-имя историческое `back_to_stats`). Тумблеры перерисовывают клавиатуру этой панели.

Карточка статьи (отправляется ФАЙЛОМ): «✅ Одобрить в базу» (для pending), «📝 Заменить», «🗑 Удалить» (с подтверждением), «⬅️ К списку».
- Подтверждения сброса промптов: prompt_reset_confirm/cancel, news_prompt_reset_confirm/cancel, rag_prompt_reset_confirm/cancel (возврат заводской RAG-инструкции), proactive_prompt_reset_confirm/cancel (возврат заводской инструкции участия). Все ВОСЕМЬ обслуживает ОДИН исполнитель `handle_prompt_reset` (panel_prompts.py) по таблице `_PROMPTS`: до 2026-08-03 в роутере лежали восемь почти дословно одинаковых веток на ~110 строк. Тексты и попапы не менялись ни на символ — сверено прогоном всех восьми кнопок против прежнего кода.

### 2.4 Антифлуд (services/antispam.py) — как есть в коде
- По умолчанию ВЫКЛЮЧЕН (`ANTISPAM_ENABLED_DEFAULT = "0"`); включается в /mod. Настройки глобальные на все группы.
- Детектор: ≥N сообщений за окно (дефолт 5 за 5 сек), счётчик в памяти процесса (сбрасывается при рестарте — это нормально).
- Срабатывание: временный мут через `restrict_chat_member` (дефолт 300 сек) → **удаление всего спам-всплеска** → запись в `moderation_log` + **тексты удалённых сообщений в `mute_evidence` (улики) ДО удаления** → сообщение в чат «🛡 X получает мут…» с кнопкой «🔓 Размутить».
- Защищены от мута: ADMIN_IDS, сам бот, админы/владелец Telegram-группы; если статус проверить не удалось — НЕ мутим (безопасный дефолт).
- Пока мут активен, «протёкшие» сообщения нарушителя добиваются поштучно.
- Размут (`unmute()`): восстанавливает ДЕФОЛТНЫЕ права группы (не «всё разрешено»), пишет unmute в журнал с именем админа (параметр admin_name — передают кнопка и /unmute). Вызывается кнопкой и командой /unmute.
- Статистика в /mod: мутов/размутов за 7 дней (`MOD_STATS_DAYS`), последние 5 действий (у размутов приписка «(снял: …)» — из admin_name; старые записи без неё), просмотр улик по кнопке. Хранение 7 дней, чистится cleanup_loop.
- **Альбомы фотографий (2026-07-19):** Telegram шлёт альбом как НЕСКОЛЬКО сообщений с общим `media_group_id` — без поправки альбом из 5 фото мгновенно выбирал порог и человек получал мут ни за что (наступили на этом). Теперь `collect_group_message` передаёт `media_group_id` в `check_and_mute`, а размер всплеска считает `_count_messages`: части одного альбома схлопываются в единицу, РАЗНЫЕ альбомы считаются по отдельности (залп альбомами ловится). В памяти при этом остаются ВСЕ части (удаление спама и улики работают как раньше).
- **Персональные настройки участника (2026-07-20, карточка /users).** Общие пороги перекрываются личными по каждому полю отдельно: `get_thresholds()` — общие (панель /mod), `get_thresholds_for(user_id)` — с учётом личных (её зовёт `check_and_mute` и мут за повторные ссылки). Тумблер «иммунитет» (`antispam_immune`) — автоматика такого человека НЕ мутит вообще: проверяется в самом начале check_and_mute (до регистрации сообщения в счётчике) и отдельно перед мутом за повторные ссылки; на УДАЛЕНИЕ ссылок иммунитет не влияет — для этого свой тумблер `links_allowed` в начале `check_and_delete_links`. Ручного статуса «проверенный» БОЛЬШЕ НЕТ (`trusted_manual` удалён 2026-07-20 вместе с тумблером карточки): `trust_info` считает статус только автоматикой, поля `manual` в её ответе нет; графа `trusted_manual` в `user_settings` осталась в БД мёртвой (как `p_antispam` в staff) — из белого списка `_USER_SETTING_FIELDS` убрана.
- Прогрессивных наказаний НЕТ (MVP — всегда один и тот же мут).
- **Личное дело и статус «проверенный» (2026-07-15):** на каждого участника групп копится вечная запись `user_dossier` (стаж first_seen, msg_count — пишет collect_group_message, mute_count/last_mute_ts — оба пути мута, link_count — фильтр ссылок). Правило доверия ОДНО — `antispam.trust_info(user_id)`: стаж ≥ `TRUST_MIN_DAYS`(7) И сообщений ≥ `TRUST_MIN_MESSAGES`(100) И мутов нет (или последний старше `TRUST_FORGIVE_DAYS`(30) — прощение). ⚠️ БОНУСА К ПОРОГУ АНТИФЛУДА БОЛЬШЕ НЕТ: `TRUST_EXTRA_MESSAGES` удалена 2026-07-20 (решение Максима), проверенный мутится наравне со всеми; статус чисто информационный — его показывают /rank, карточка /users и справка об авторе в проактивном режиме, `check_and_mute` его не читает. /rank показывает блок «🪪 Служба в гарнизоне» (стаж, сообщения, статус) через тот же trust_info. Стаж копится с момента внедрения (дата вступления в группу у Telegram не запрашивается).
- **Фильтр ссылок (2026-07-14, `check_and_delete_links`):** отдельный тумблер «🔗» в /mod (ключ `linkfilter_enabled`, дефолт ВЫКЛ, НЕ зависит от тумблера антиспама). Ловит entity url/text_link в тексте И подписи к фото (разбор только через `parse_entities` — смещения UTF-16!). Белый список `LINKFILTER_WHITELIST` (config.py, дефолт wtmobile.com; поддомены проходят, подделки вида wtmobile.com.evil.ru — нет). Защищённые (`_is_protected`) не трогаются. Действие: удалить сообщение → журнал `moderation_log` (action="linkdel") + улика в `mute_evidence` → предупреждение в чат (самоудаляется 15 сек). За `LINKFILTER_MUTE_COUNT`(3) удалений за `LINKFILTER_WINDOW_SEC`(час) — временный мут обычной длительности (ключ antispam_mute_sec) с кнопкой размута; счётчик повторов `_link_strikes` в памяти. Вызов — из collect_group_message ПОСЛЕ антиспама и только если тот не замутил. Ограничение: видит только текст/фото (фильтр group=1), обходы «точка ком» не ловит.
- **Уведомление модераторов об автоматическом муте (2026-07-20):** после мута за флуд И после мута за повторные ссылки `_notify_moderators_mute` шлёт в личку МОДЕРАТОРАМ (только тем, у кого есть право `mod` — остальным кнопка всё равно не нажмётся) сообщение с названием группы, причиной и кнопкой «🔓 Размутить». ВЛАДЕЛЬЦАМ намеренно НЕ шлётся: у них есть панель /mod с полным журналом (захочешь — одна строка в функции). Ручные муты из карточки уведомления не порождают — их сделал человек, и они видны в журнале персонала. Функция «тихая», как вся antispam.py.
- **Иерархия персонала (2026-07-20):** `_is_protected` не даёт автоматике мутить ВЕСЬ персонал (`roles.is_staff` — владельцы и модераторы). У ручных действий своя охрана `_manual_guard(bot, target_id, actor_id)`: владелец может ко всем, модератор — только к обычным участникам (ни к владельцу, ни к другому модератору, ни к себе; правило одно — `roles.can_act_on`). Все ручные действия принимают `actor_id` — не забыть передать его из панели, иначе охрана вернётся к старому правилу «персонал не трогаем» и модератор сможет мутить модератора. Потолок срока мута для модератора — `config.MODERATOR_MAX_MUTE_SEC`, проверяется ДВАЖДЫ: длинные сроки не показываются на кнопках И отбиваются при выполнении (нажатие старой кнопки не должно обходить лимит).
- **Ручные действия админа (2026-07-20, кнопки карточки /users):** `mute_user` (мут на выбранный срок), `unmute` (был), `kick_user` (в Telegram это бан + немедленное снятие — иначе человек не сможет вернуться), `ban_user`, `unban_user`. Возвращают ПУСТУЮ строку при успехе или текст ошибки Telegram (панель показывает его во всплывающем окне) — в отличие от автоматики, которая всё глушит молча. Проверку `_is_protected` они НЕ применяют (админ группы вполне может быть целью), вместо неё `_manual_guard`: нельзя трогать админов бота из ADMIN_IDS и самого бота. Всё остальное разрешает или запрещает Telegram.
- **Типы записей журнала модерации:** `mute` (автоматика), `mute_adm` (ручной мут), `linkdel`, `unmute`, `kick`, `ban`, `unban`. Панель /mod перечисляет их ЯВНО (словарь `icons` в `_build_mod_panel_text_and_keyboard`): раньше «всё остальное» рисовалось как размут, и с приходом ручных действий журнал начал бы врать. Улики (`mute_evidence`) есть только у `mute` и `linkdel` — кнопка «📜» показывается только им. Графа `admin_name` теперь показывается у ВСЕХ ручных действий («снял:» у размута/разбана, «админ:» у остальных).
- Вся модерация «тихая»: любое исключение глушится, бот не падает.

### 2.5 Автоматическое поведение
- **ИИ-ответы:** личка — на всё; группа — только при @упоминании (в тексте или подписи к фото/видео) или Reply на сообщение бота. Фото — анализ (если активная модель без поля vision — DeepSeek/Qwen — фото ей не отправляется: vision-reroute сразу на цепочку Gemini, без уведомления админам), голос/аудио — через `AUDIO_FALLBACK_CHAIN`, ВИДЕО (2026-07-24) — через `VIDEO_FALLBACK_CHAIN` с проверкой поля `"video"`; подпись к видео уходит модели как вопрос, статус «🎬 Смотрю видео…» удаляется после ответа. Видео больше 20 МБ (`VIDEO_MAX_BYTES`) бот не скачивает — Telegram столько и не отдаёт — и честно отвечает, что ролик великоват. Статус «печатает…» висит всё время генерации.
- **RAG при ответах:** каждый текстовый запрос (и подпись к фото) уходит в гибридный поиск (один дешёвый вызов эмбеддинга, кэш повторов на 128 запросов); статьи, прошедшие отбор (балл = смысл + слова, «пик против полки» — см. services/rag.py), попадают в системный промпт ЦЕЛИКОМ под «шапкой»-инструкцией (`get_rag_instruction`: своя из settings `rag_instruction` или заводская `RAG_INSTRUCTION`; правится из /prompt командами /rag_prompt_*), формат каждой статьи «=== РАЗДЕЛ: … ===». Работает НЕЗАВИСИМО от тумблера «PROMPT ВЫКЛ» (решение 2026-07-05), но подчиняется ОБЩЕМУ тумблеру «📖 База знаний» панели /rag (settings `rag_enabled`, с 2026-07-27 — один на весь бот; проверка внутри `rag.retrieve_relevant_context`, поэтому её слушаются все пути сразу: личка, группы, «Сам в разговор»). Голосовые RAG не используют (аудио уходит модели напрямую).
- **Добор базы знаний (2026-07-19, jobs/rag.py::rag_catchup_loop):** раз в час проверка полноты векторного индекса (`rag.index_lag()` — сравнение файлов и mtime, БЕЗ запросов к Google). Индекс полный → тишина (ни лога, ни запросов). Неполный (сбой квоты Google) → обычная синхронизация недостающего под той же защёлкой `kb_rebuild_running` (идущую ручную пересборку не трогает — пропускает свой час). Уведомления админам в личку ТОЛЬКО на границах инцидента: одно «⚠️ база неполная X из Y» при первой неудаче добора, одно «✅ снова полная» при выздоровлении; между ними — строки в логе раз в час. Первая проверка через час после старта (стартовую синхронизацию делает main.py). Сообщения не регистрируются в гигиене панелей — остаются в чате как история.
- **Архив групп (`collect_group_message`, group=1):** пишет сообщения групп в `group_messages` и зовёт антиспам. Фильтр — `TEXT|PHOTO|VOICE|AUDIO|VIDEO`: голосовые и аудио попадают с 2026-07-21 (графа `has_voice`), видео с 2026-07-24 (`has_video`). СТИКЕРЫ, КРУЖОЧКИ (VIDEO_NOTE) и ГИФКИ (ANIMATION) не попадают — их не видит и антиспам. С 2026-07-16 в архив пишутся и СВОИ ответы бота в группах (прямые — через `_archive_bot_group_reply`, проактивные — из `_run_proactive`): собственные сообщения апдейтами не приходят, а стенограмма «Сам в разговор» должна видеть, что бот уже говорил.
- **«Сам в разговор» (2026-07-16, services/proactive.py):** тумблер `proactive_enabled` в панели промптов, дефолт ВЫКЛ. На каждое сообщение группы (в конце collect_group_message, только если не было ни мута, ни удаления ссылки) — дешёвые фильтры: защёлка «в полёте», не бот (защита от петли бот-бот), не команда, не игнор из карточки (`ai_ignored`), не прямое обращение, тумблер, порог новых сообщений (`proactive_min_msgs`). СУДЬЯ УДАЛЁН 2026-07-20: быстрые модели без мышления плохо следуют инструкциям. Прошло всё → отдельной задачей ОДИН запрос `ask_group_proactive` (активная думающая модель И решает, И пишет): стенограмма последних N сообщений («Ты: …» — свои; N — регулятор «📜 контекст» панели, ключ `proactive_context_msgs`, дефолт `PROACTIVE_CONTEXT_MSGS`=25) + характер + RAG по триггеру + инструкция (`get_proactive_instruction`, включает блок рук — модель видит его всегда); модель пишет реплику ИЛИ слово «ПРОПУСК» (маркер ищется в видимой части, без `<thought>`). Запрос идёт через АКТИВНУЮ модель с обычной цепочкой подстраховки. Реплика уходит В ЧАТ С МЫСЛЯМИ (свёрнутый блок). Стенограмму можно обнулить кнопкой «🧹Очистить РАЗГОВОРЫ».
- **Новости:** каждые 10 мин скрейпинг wtmobile.com/ru → форматирование моделью (промпт `news_system_prompt`) → рассылка подписчикам альбомом (главная картинка + 1 карточка ТТХ; текст ≤1024 — подписью, иначе отдельно) → исходный текст в `knowledge/pending/`. С 2026-07-17 при отправке в ГРУППУ (chat_id < 0) сводка новости пишется в архив групп (`save_group_message` в конце `send_news_to_chat`) — попадает в стенограмму «Сам в разговор»; при полном провале отправки записи нет; `note_bot_group_reply` НЕ вызывается (намеренно — см. часть `references/dependencies-*.md`); в личные чаты архив не ведётся.
- **Викторина:** после ответа любого участника через 2.5 сек автоматически следующий вопрос (ровно один раз на опрос; пауза — отложенной задачей, бот в это время не стоит); каждый опрос автоудаляется через 60 сек; повышение звания → поздравление в ЛС.
- **Очередь апдейтов (2026-07-13):** апдейты обрабатываются по одному (concurrent_updates НЕ включён — вариант А аудита отложен), НО пять долгих хендлеров (текст/фото/голос/видео → ИИ и /imagine) зарегистрированы с `block=False` и выполняются отдельными задачами — долгий ответ нейросети одному пользователю больше не морозит остальных, панели, антиспам и архив групп. Побочный эффект: два вопроса от одного человека подряд могут обрабатываться параллельно (ответы придут в произвольном порядке) — принято как допустимое.
- **Гигиена сообщений:** новое «панельное» сообщение бота удаляет предыдущее в том же чате (`bot_sent_messages`, переживает рестарт); команды пользователей удаляются; служебные подтверждения самоудаляются через 15–30 сек.
- **Лог команд (2026-07-13):** каждая входящая команда пишется в лог строкой «⌨️ Команда: … | от … | личка/чат» центральным регистратором `log_incoming_command` (handlers/commands.py, group=-1) — до основных обработчиков, текст длиннее 100 символов обрезается. Старые точечные строки лога команд, «скрытые по просьбе» в 2026-07, НЕ раскомментировывать — их заменяет регистратор. Выключается одной строкой регистрации в handlers/__init__.py.
- **Запуск:** убийство старой копии по bot.pid (кроме Docker) → уведомление ПЕРСОНАЛУ «✅ Бот запущен» → авто-открытие панели каждому (она затирает уведомление; у модератора панель собрана по его правам). Получателей считает `main._staff_recipients()`: владельцы + модераторы, у которых есть хоть одно право (модератора без прав дёргать при каждом перезапуске незачем). ЭТО ТОЛЬКО про запуск/остановку — итоги месяца, расходы, сбои моделей и состояние базы знаний остаются ВЛАДЕЛЬЦАМ (jobs.py, gemini.py читают ADMIN_IDS напрямую).
