**Команды, которые нужны чаще всего** (выполняются с ПК Максима):

```
ssh c4max "systemctl status c4max-bot"     # жив ли
ssh c4max "journalctl -u c4max-bot -n 50"  # свежие строки лога
ssh c4max "systemctl restart c4max-bot"    # перезапустить
ssh c4max c4max-update                     # забрать код с GitHub и перезапустить
```

⚠️ Эти команды работают **из PowerShell**. Из Git Bash тот же `ssh c4max`
падает с «Could not resolve hostname»: `~` там разворачивается мимо
`C:\Users\С4\.ssh\config`, и короткое имя не читается (сверено 28.08.2026).

⚠️ Любая команда `git` в `/home/c4bot/bot` из-под `root` падает с «detected
dubious ownership»: папка чужая. Не чинить глобальным `safe.directory`, а
дописывать к самой команде — `git -c safe.directory=/home/c4bot/bot log`.
Сверено 2026-11-02: сервер = `main` на GitHub, рабочая копия чистая,
Ubuntu 24.04.5, Python 3.12.3, python-telegram-bot 22.8 (дома 22.7).

**Чем сервер отличается от домашнего компьютера — важное для правок кода:**

- `IS_DOCKER` там **True** (считается автоматически: не Windows → управляемая
  среда). Отсюда: `bot.pid` не пишется, старые копии не убиваются, а кнопка
  «🔄 ПЕРЕЗАПУСК» просто завершает процесс с кодом 1 — поднимает его
  systemd. Уберёшь `Restart=always` из службы — кнопка станет кнопкой
  выключения.
- Логи идут **в journalctl**, а не только в файлы `logs/`. Файлы тоже пишутся,
  их отдаёт кнопка «📜 Логи бота».
- **Windows-приспособления там не работают и не нужны:** `watchdog_local.py`
  (задание планировщика, ctypes), новое окно консоли при перезапуске,
  `taskkill` по `bot.pid`. Код это уже учитывает — не «чинить».
- Снаружи открыты **SSH, 80 и 443** (ufw), вход по паролю выключен
  (`/etc/ssh/sshd_config.d/00-c4max.conf` — файл `00-` нужен, чтобы
  перебить `50-cloud-init.conf` хостинга), подбор паролей банит `fail2ban`.
  Порты 80/443 — под веб-админку, см. раздел «Сайт» ниже.
- ⚠️ **`fail2ban` в Ubuntu 24.04 из коробки слепой:** его фильтр ищет в
  журнале службу `sshd.service`, а она называется `ssh.service`, — и не
  блокирует никого. Поэтому в `/etc/fail2ban/jail.local` прописан
  `journalmatch` с `ssh.service`.
- `.env` и `history.db` лежат на сервере и **через GitHub не ездят никогда**.
  Меняешь ключ — меняй на сервере отдельно.
- Папка `knowledge/` (статьи базы знаний) тоже не ездит — с v4.23. Новые
  статьи появляются ТОЛЬКО на сервере, домашняя копия отстаёт (31.10.2026:
  дома 120 файлов против 132 на сервере, и у 49 общих текст старый).
  Считаешь, каких статей не хватает викторине, или сверяешь по статьям
  числа, — считай по серверу, иначе получишь «всё покрыто» и это будет
  неправдой. Домашнюю папку делает копией серверной
  `python .claude/skills/quiz-questions/scripts/quiz_tool.py pull`.
- **Правишь боевую базу руками — только от имени `c4bot`** (`sudo -u c4bot
  python3 …`). Вход по ssh даёт root, а база живёт в режиме WAL: запись от
  root оставляет рядом root-овы `history.db-wal` и `-shm`, и бот после этого
  писать в базу не может. По той же причине копию нельзя снимать простым
  `cp` — часть свежих записей лежит в журнале; берётся она через
  `sqlite3.Connection.backup`. Останавливать бота при этом не нужно: WAL
  разводит короткую правку со стороны и работу бота (проверено 21.08.2026
  на 219 строках банка вопросов).
- Папка `backups/` (ночные копии базы, 2026-07-31) — там же и тоже мимо
  GitHub: это те же живые данные. Копия за прошлую ночь есть и у Максима
  в личке — если сервер недоступен, восстанавливаться оттуда.
- ⚠️ **Переносишь `knowledge/` архивом — сохрани точное время файлов.**
  Индекс базы знаний (`services/rag.py`) сверяет время изменения статьи до
  долей секунды, а обычный `tar` округляет его до секунды. Тогда бот примет
  все статьи за изменённые и начнёт заново просить у Google вектора — по
  3,5 с на статью, и всё это время НЕ отвечает в Telegram (индексация идёт
  до запуска опроса). Лечение — `tar
  --format=posix` при упаковке либо время из самого индекса
  (`knowledge_base_vectors.json`, поле `mtime`) через `os.utime` до запуска.
- Файлы, которые бот перезаписывает сам, **не должны быть в репозитории**
  (например `knowledge/knowledge_base_vectors.json`) — иначе обновление
  упрётся в «файл изменён и там, и тут».
- **Папка `knowledge` целиком принадлежит серверу** (с 12.08.2026, v4.24):
  статьи и новости пишет там сам бот, а в git её больше нет вовсе. До этого
  85 файлов в ней ОТСЛЕЖИВАЛИСЬ и роняли обновление целиком: `git merge
  --ff-only` не кладёт приходящие файлы поверх неотслеживаемых серверных и
  отказывается вместе с кодом — так сорвалась выкатка v4.21 (2026-08-11,
  подробности в `history.md`). Возвращать её в репозиторий нельзя: батник
  шлёт `git add -A`, и грабли встанут на прежнее место. Запасной экземпляр
  статей — архив владельцу в личку каждую ночь (`services/backup.py`).
**Обвязка системы:**

- Системному журналу задан потолок `SystemMaxUse=200M`
  (`/etc/systemd/journald.conf`, исходный файл рядом как `.bak-orig`).
  Понадобится глубокая история `journalctl` — потолок придётся поднять,
  старое затирается само. Потолок уже выбран: 02.11.2026 журнал занимал
  198,6 МБ и хранил около трёх недель — с 10.10.2026.
- Подкачка — файл `/swapfile` на 2 ГБ (так пришёл образ хостинга).
  Загрузка BIOS, не EFI.
- Автоматические обновления системы выключены
  (`/etc/apt/apt.conf.d/20auto-upgrades`, оба значения `0`) — ставятся
  вручную. Последний раз 02.11.2026: 59 пакетов (45 — исправления
  безопасности), ядро 6.8.0-147, перезагрузка — бот молчал 15 с. Порядок:
  проба `apt-get -s full-upgrade` (ничего не удаляет?) → установка
  отдельной задачей `systemd-run` (обрыв ssh её не прервёт), конфиги
  прежние (`--force-confold`), `NEEDRESTART_SUSPEND=1` → новый вход по ssh
  → записка `/home/c4bot/.c4max-restart-planned` от `c4bot` (сторож
  промолчит) → перезагрузка.
- ⚠️ **После обновления программы входа служба `ssh` значится `inactive`, а
  `sshd -t` жалуется на `/run/sshd` — это не поломка.** В Ubuntu 24.04 дверь
  держит `ssh.socket` и поднимает службу при первом подключении. Проверка —
  новый вход по ssh, а не `systemctl is-active ssh`.
- Счётчики `fail2ban-client status` после перезагрузки начинаются с нуля.

- Управление самим сервером (стоп/старт/перезагрузка, VNC, переустановка) —
  в личном кабинете s-host. **«Стоп» + «Старт» безопасны:** бот поднимется сам,
  ничего не теряется; сторож healthchecks.io пришлёт тревогу «не отвечает» и
  потом «снова работает» — это ожидаемо, он не отличает выключение от аварии.
- **Откуда тревоги сторожа:** сетевые провалы хостинга (в журнале бота —
  «отметка НЕ прошла»: таймауты до Telegram и hc-ping.com) и перезагрузки
  самой виртуалки без штатного выключения (`last -x reboot`). Жалоба на
  тревоги — сначала посчитать то и другое по дням, а не править код.
  Отправка с ПК, которая перезапускает бота (`c4max-update` → `systemctl
  restart`), сторожа не будит: с v5.57 она оставляет боту записку
  `/home/c4bot/.c4max-restart-planned`, и хук остановки молчит (см.
  `wiring.md`, `post_stop`).

## Сайт (веб-админка) — с 30.08.2026

Второй способ управлять ботом, кроме кнопок в Telegram. Кнопки при этом
остались все: сайт — вторая дверь, а не замена (решение Максима).

| Что | Где |
|---|---|
| Адрес | `https://c4max.duckdns.org` |
| Имя | бесплатное на DuckDNS, счёт Максима; s-host своего имени не даёт вовсе |
| HTTPS | Caddy 2.6.2 из репозитория Ubuntu, сертификат Let's Encrypt, продлевает сам |
| Настройка Caddy | `/etc/caddy/Caddyfile` (в репозитории бота ЕЁ НЕТ — правится на сервере) |
| Журнал обращений | `/var/log/caddy/access.log`, 10 МБ × 3 файла |
| Сам сайт | внутри процесса бота, `127.0.0.1:8080` (`jobs/web.py` + пакет `web/`) |
| Включение | `WEB_ENABLED=true` и `WEB_PUBLIC_URL` в `/home/c4bot/bot/.env` |
| Продление имени | `/root/duckdns-update.sh` по cron в 17 минут каждые 5 часов |

**Что из этого НЕ едет через GitHub и живёт только на сервере:**
`/etc/caddy/Caddyfile`, `/root/duckdns-update.sh`, строка cron, две строки
`WEB_*` в `.env`, правила `ufw`.

**Переезд на другой сервер (бот молчит около двух минут):**
всё готовится заранее при работающем старом — пользователь `c4bot`, ключ
к GitHub (`/home/c4bot/.ssh/github_deploy` + `config`, тот же, что на
старом), клон репозитория, `.venv` по `pip freeze` старого, служба
`c4max-bot` (описана, но НЕ включена — две копии с одним токеном нельзя),
`/usr/local/bin/c4max-update` из `deploy-restart.sh`, Caddy с `Caddyfile` и
ПАПКОЙ СЕРТИФИКАТОВ старого (`/var/lib/caddy/.local/share/caddy`) — тогда
после переключения сайт сразу открывается без окна «небезопасно»;
`.env`, затем обе проверки бота на новом. Само переключение: старый —
`stop` + `disable` + строку DuckDNS в cron закомментировать; база —
через `sqlite3 backup`, вместе с `knowledge/` (см. ловушку про время
файлов выше), `backups/`, `logs/`; новый — `enable --now`, разовый запуск
`/root/duckdns-update.sh` + строка cron, `enable --now caddy`; на ПК —
`HostName` у `c4max` в `~/.ssh/config`.

⚠️ **Останов бота = сайт отвечает 502.** Это не поломка Caddy и не поломка
сайта: сайт и есть бот. Кнопка «🔄 Перезапустить бота» на сайте (страница
`/system`, есть с 30.08.2026) неизбежно обрывает саму страницу — так и
задумано: страница предупреждает об этом до нажатия и спрашивает
подтверждение.

⚠️ **Имя на DuckDNS протухает, если его 30 дней не обновлять.** Отсюда cron.
Пропали отметки в `journalctl -t duckdns` — имя перестанет открываться
примерно через месяц, и выглядеть это будет как «сайт исчез».

⚠️ **Токен DuckDNS лежит в `/root/duckdns-update.sh`** (права 700), а НЕ в
строке cron: строку cron видно в списке процессов любому, кто на машине.

Полезные команды:

```
ssh c4max "systemctl status caddy"                  # жив ли HTTPS
ssh c4max "journalctl -u caddy -n 30 --no-pager"    # что с сертификатом
ssh c4max "journalctl -t duckdns -n 5 --no-pager"   # обновляется ли имя
ssh c4max "ss -tlnp | grep 8080"                    # поднялся ли сайт в боте
curl -s https://c4max.duckdns.org/health            # ответ снаружи: ok
```
