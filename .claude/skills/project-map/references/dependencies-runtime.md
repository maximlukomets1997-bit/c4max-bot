- **🐕 Трогаешь сторожа (2026-07-27)** → пять правил. ⛔ Сначала имей в виду: МЕСТНЫЙ сторож с вечера 2026-07-27 ВЫКЛЮЧЕН заданием планировщика (Disabled), работает только внешний. Правила ниже писались при обоих живых и остаются верны — просто половина из них сейчас спит. Включаешь местный обратно (`schtasks /change /tn "C4_Max Bot Watchdog" /enable`) — перечитай их все. (1) `watchdog_loop` обязан работать ДАЖЕ БЕЗ `WATCHDOG_URL` — выход в начале функции возвращать нельзя: без него не пишется метка `bot.alive`, и местный сторож поднимет вечную ложную тревогу (наступил на этом при написании). (2) Отметка идёт ТОЛЬКО после удачного `get_me` — это и делает её осмысленной («бот достаёт до Telegram», а не «процесс запущен»); безусловная отметка молчала бы при недоступном Telegram. (3) `WATCHDOG_PING_SEC` (1 мин) должен быть заметно МЕНЬШЕ, чем Period + Grace Time в настройках проверки на healthchecks.io (у Максима 1 + 2), иначе тревоги станут ложными; меняешь одно — поправь второе, вторая половина настройки живёт НЕ в коде, а в личном кабинете сервиса. (4) `WATCHDOG_STALE_SEC` (3 мин) должен быть больше `WATCHDOG_PING_SEC` с запасом — иначе одна пропущенная отметка (моргнул интернет) поднимет местную тревогу. ⚠️ ИМЕННО ЭТО ЧИСЛО, А НЕ ЧАСТОТА ПРОВЕРОК, решает, как быстро придёт тревога о зависшем боте — выяснено на настоящей аварии 2026-07-27. И оно же — главный регулятор ложных тревог: раздражают — поднимать его, а не выключать сторожа. (6) Меняешь темп — меняй ОБА конца: числа в config.py И Period/Grace в личном кабинете healthchecks.io. Порядок важен: сначала код и перезапуск бота, потом затягивание сроков на сервисе, иначе получишь ложную тревогу в промежутке (наступил на этом 2026-07-27 — пришлось ставить проверку на паузу). (5) `watchdog_local.py` НЕ импортировать из кода бота и не тащить в него зависимости от `services`/`database`: он обязан работать, когда бот сломан. И ⚠️ никогда не проверять процесс через `os.kill(pid, 0)` — в Windows это ЗАВЕРШАЕТ процесс, сторож убьёт бота.

- **`.env` И КНОПКА ПЕРЕЗАПУСКА (2026-07-24)** → `load_dotenv(override=True)` в config.py — файл ГЛАВНЕЕ окружения, и снимать `override` нельзя. Кнопка «🔄 ПЕРЕЗАПУСТИТЬ БОТА» порождает копию через `subprocess.Popen`, а та НАСЛЕДУЕТ окружение старой; без `override` dotenv не перезаписывает уже имеющиеся переменные, и ключ, прочитанный самой первой копией, тащился по всей цепочке перезапусков — правки `.env` игнорировались МОЛЧА (ни лога, ни ошибки). Наступили 2026-07-24: после смены рабочего пространства Qwen бот несколько часов слал СТАРЫЙ ключ на НОВЫЙ адрес и получал 403 с пустым телом; лечилось только полным перезапуском из консоли. Диагностический признак: 403 «Forbidden» = ключ живой, но от ДРУГОГО пространства; 401 «Invalid API-key» = ключ удалён. Новая переменная в `.env` — проверять правку прогоном дочернего процесса с подставленной старой переменной в окружении, а не глазами. ⚠️ В Docker переменные задают окружением: появится там ещё и `.env` — он теперь перебьёт настройки контейнера.
- **Окно консоли при перезапуске (2026-07-24, просьба Максима — вернуть как было)** → в Windows новая копия запускается с `creationflags=subprocess.CREATE_NEW_CONSOLE`: своё чистое окно, старое закрывается вместе с процессом. Без флага Windows отдаёт копии окно РОДИТЕЛЯ, и логи всех перезапусков идут в одно окно сплошной лентой (так вело себя с ~20.07 — заметил Максим 24.07). Флаг существует ТОЛЬКО в Windows, на других системах `Popen` бросит ValueError — проверка `sys.platform == "win32"` обязательна, словарь `extra` пустой во всех прочих случаях. На ФАЙЛЫ логов это не влияет никогда: имя файла даёт `logging_setup`, каждый запуск пишет свой. ⚠️ Побочный эффект: если новая копия падает на старте, её окно закрывается мгновенно и человек видит только исчезнувшего бота — причину искать в `logs/` (setup_logging зовётся первым, до импорта модулей бота, поэтому в файл попадает почти всё).
- **Меняешь механику рестарта** → связка: кнопка ставит `bot_data["shutdown_reason"]="restart"` → post_stop молчит → main() после run_polling зовёт `_restart_self()`; при `IS_DOCKER=true` — просто выход.
- **⚡ Кнопка перезапуска в управляемой среде выходит с КОДОМ 1 (2026-07-27)** → при `IS_DOCKER=true` после `_restart_self()` в `main()` стоит `sys.exit(1)`. Это НЕ баг и не забытая отладка: панель хостинга поднимает бота только после сбоя, а корректный выход (код 0) считает за «остановлен вручную» — проверено на UkrLine, кнопка гасила бота насмерть. Обычная остановка (Ctrl+C, кнопка «Стоп») кода не меняет: там `shutdown_reason` не выставлен. ⚠️ Побочный эффект: панель может присылать уведомление «бот упал» на каждый перезапуск кнопкой — это ожидаемо. ⚠️ Дома (Windows, IS_DOCKER=false) выход остаётся нулевым, копию рождает сам бот.

И помни: кнопка работает, только пока бот жив, а обновляются чаще всего когда он сломан, — поэтому основной способ навсегда остаётся `.bat` с компьютера.

- **⚡ IS_DOCKER теперь зависит от системы (2026-07-27)** → значение по умолчанию считается в `config.py`: на Windows `false` (бот сам сторожит единственность через `bot.pid` и сам порождает копию при перезапуске), на ЛЮБОЙ другой системе `true` (процессом управляет панель хостинга/контейнер). (6) Удаление тихое по смыслу, но НЕ безмолвное в логе: сообщение мог убрать сам владелец, а старше 48 часов Telegram ботам удалять не даёт — оба случая штатные, новое уведомление отправляется в любом случае, но в лог идёт `warning` (до 2026-08-05 стоял `debug`, и не сработавшая уборка не оставляла следа — именно это мешало разобраться). След снимается ДАЖЕ ПРИ НЕУДАЧНОМ удалении, иначе бот ломился бы в то же сообщение при каждом запуске вечно.
