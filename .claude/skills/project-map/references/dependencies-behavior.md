# Зависимости: Сообщения, медиа, модерация и «Сам в разговор»

«Меняешь X — проверь Y». Часть общего раздела зависимостей карты проекта;
соседние части перечислены в `SKILL.md`.

- **Объявление «БАН» при выключении режима «Сам в разговор» (2026-07-24, просьба Максима)** → текст `PROACTIVE_OFF_ANNOUNCE` в config.py продиктован им ДОСЛОВНО, формулировку не править и не «улучшать»; обратного объявления («бан снят») он НЕ хочет — включение просто удаляет сообщение. Механика: `_announce_proactive_off` / `_remove_proactive_off_announce` в panel_prompts.py, координаты отправленных сообщений — список пар `[chat_id, message_id]` в JSON, ключ settings `PROACTIVE_OFF_MSGS_KEY`. Три правила, которые нельзя «чинить»: (1) объявление НЕ регистрируется в гигиене панелей (`register_and_clean_bot_message`) — иначе его затрёт первая же панель, а висеть оно должно до включения режима; (2) координаты только в БД, не в памяти — иначе перезапуск бота, и удалять нечем, объявление зависнет навсегда; (3) сбой отправки/удаления в одной группе молча пропускается и НЕ ломает переключение тумблера (сама ветка `toggle` тоже обёрнута в try). Рассылка идёт по `get_known_chats()` — новая группа подхватится сама, как только бот увидит там сообщение. ⚠️ Telegram не даёт ботам удалять сообщения старше 48 часов: режим, выключенный дольше двух суток назад, оставит объявление в группе навсегда — удалять руками.
- **⚠️ ЗАШИТЫЕ ФРАЗЫ-ИНСТРУКЦИИ К МЕДИА УДАЛЕНЫ (2026-07-24, решение Максима)** → модели уходит ТОЛЬКО файл, без единого слова от бота. Удалены все пять: «Кратко опиши, что на этом фото…» (`_proactive_describe_image`), «Расшифруй это голосовое сообщение…» (`_proactive_transcribe_audio`), «Опиши КРАТКО… что происходит на этом видео» (`_proactive_describe_video`), «Ответь на это голосовое сообщение пользователя.» (`ask_gemini_audio`) и заготовка для видео без подписи (`ask_gemini_video`). Повод: Максим не хочет, чтобы бот подсказывал моделям формулировки от себя (претензия была именно к тому, что фразы сочинены и зашиты без его ведома). НЕ возвращать ни одну из них по своей инициативе — только по прямой просьбе. Добавляя новый вид медиа, фразу-инструкцию тоже НЕ сочинять: шли голый файл. ⚠️ ИЗВЕСТНОЕ ПОСЛЕДСТВИЕ, принято Максимом осознанно («оставить как есть»): в ПРЯМЫХ ответах стало лучше (характер бота из `systemInstruction` ведёт модель сам — проверено живым тестом, ответы в образе и по-русски), а в ПРОАКТИВНОМ разборе характера нет, и модель отвечает как хочет — на живом тесте описания фото и видео пришли ПО-АНГЛИЙСКИ, списками и с таймкодами, а вместо расшифровки голосового модель начала сама отвечать на вопрос. Всё это попадает в стенограмму беседы. Увидишь английский/списки в стенограмме — это не баг, а следствие этого решения.
- **Трогаешь ВИДЕО (2026-07-24)** → четыре правила. (1) Потолок `VIDEO_MAX_BYTES` = 20 МБ — это предел Telegram Bot API на скачивание файла ботом, обойти его нельзя; проверять `video.file_size` ДО `get_file()`, иначе тянем впустую, а человек не понимает, почему бот молчит. `file_size` иногда не приходит — тогда пробуем скачать, падение ловит общий `except`. (2) Обработчик зарегистрирован на `filters.VIDEO` и ТОЛЬКО на него: кружочки (`VIDEO_NOTE`) и гифки (`ANIMATION`) Максим обрабатывать не захотел — не добавлять «до кучи». (3) Цепочка `VIDEO_FALLBACK_CHAIN` задаёт ПОРЯДОК, а право на видео проверяется полем `"video"` через `_supports_video` — модель без поля в запрос не попадёт даже из цепочки. Новая модель, принимающая видео → поставь ей `"video": True` в config, иначе видео ей не отправится. (4) В проактивном режиме свой, БОЛЕЕ НИЗКИЙ потолок `PROACTIVE_VIDEO_MAX_BYTES` = 8 МБ: прямое обращение к боту — просьба человека, а проактив срабатывает на КАЖДОЕ видео в группе. Ролик крупнее остаётся в стенограмме пометкой «[видео]» без описания. Размер неизвестен → в проактиве видео НЕ разбирается (лучше пропустить, чем вслепую тянуть 20 МБ на каждой проверке).
- **Новый ДОЛГИЙ хендлер (сетевые вызовы, run_in_executor)** → регистрировать с `block=False` (как handle_message/handle_photo/handle_voice/handle_video/cmd_imagine), иначе он заморозит всю очередь апдейтов на время работы. И наоборот: хендлеры, чувствительные к порядку (панели, антиспам, настройки), оставлять блокирующими. Внутри block=False-хендлера проверки «проверил → списал» (как лимит картинок) должны идти БЕЗ await между ними, иначе появится гонка.
- **Лимит картинок (/imagine)** → списывается ДО генерации (`register_image_call` сразу после проверки остатка, без await между ними), при неудаче возвращается (`unregister_image_call`). НЕ переносить списание «после генерации» — залп команд /imagine обойдёт лимит (хендлер неблокирующий).
- **Тумблер «бот игнорирует этого человека» (`ai_ignored`)** → проверяется в ЧЕТЫРЁХ местах: три обработчика в handlers/messages.py (`_ai_ignored` — текст, фото, голос) И `proactive.consider_message`. Забудешь проактивный режим — игнор будет обходиться: бот сам вступит в разговор в ответ на сообщение того, кого «игнорирует». На /imagine игнор НЕ влияет намеренно — для картинок есть свой лимит (0 = запрет).
- **Меняешь `collect_group_message` или `check_and_mute`** → они обязаны НИКОГДА не бросать исключения наружу (архив и модерация не должны ронять бота). То же — `proactive.consider_message` (зовётся оттуда же).
- **Меняешь подсчёт всплеска в антиспаме (2026-07-19)** → размер всплеска считает ТОЛЬКО `_count_messages` (альбом = одно отправление); единственный его читатель — проверка порога в `_register_and_check` (второй читатель, бонус «проверенным», удалён 2026-07-20 вместе с самим бонусом; докстринг `_count_messages` про это честно и пишет — сверено 2026-08-03). Записи в `_timestamps` читаются по НОМЕРУ элемента (`_burst_message_ids`, `_burst_records`) — новые поля добавлять только В КОНЕЦ кортежа.
- **Новый тип мута в журнале модерации** → добавить его В ТРИ места: словарь значков панели /mod (`panel_mod.py`), `_ACTION_TITLES` (panel_users.py, если это действие персонала) И ⚠️ `get_moderation_counts` (database/history.py) — в последнем перечислены типы, которые считаются в сводке «За 7 дней: мутов N». Забудешь третье — мут будет виден в списке последних действий, но пропадёт из счётчика, и панель начнёт занижать цифру (наступили на этом с `mute_ai` 2026-07-20, нашёл Максим).
- **Трогаешь руки (2026-07-20)** → пометку `[МУТ:…]` ищем ТОЛЬКО в ВИДИМОЙ части ответа (модель может упомянуть её в `<thought>` как пример — это не команда), а ВЫРЕЗАЕМ из всего текста (служебный маркер не должен попасть в чат ни при каких условиях). Цель мута — `trigger_user_id` из апдейта, НИКОГДА не из текста модели: иначе выдуманный ответ сможет ткнуть в произвольного человека. `actor_id=None` в `mute_user` обязателен — это и есть защита персонала (`_manual_guard`); подставишь реальный id — модератор станет доступной целью. Тумблер `proactive_hands` проверяется ДВАЖДЫ (перед запросом и перед выдачей): между ними проходят секунды. Новый тип записи журнала (`mute_ai`) обязан быть в словаре значков панели /mod И в `_ACTION_TITLES` (panel_users.py). Судья удалён 2026-07-20 — `ask_group_judge`, `PROACTIVE_JUDGE_MODEL`, `PROACTIVE_JUDGE_MODELS`, `PROACTIVE_JUDGE_YES` больше не нужны. Блок рук — внутри заводского `PROACTIVE_INSTRUCTION`, модель видит его всегда; `{max_sec}` подставляется вызовом format при первом использовании.
- **Режим «Сам в разговор» (services/proactive.py)** → `consider_message` обязана оставаться СИНХРОННОЙ (без await между проверкой фильтров и защёлкой — иначе гонка), хук в collect_group_message — только при `not muted and not deleted` (иначе Reply на удалённое сообщение). Проверка `user.is_bot` в фильтрах ОБЯЗАТЕЛЬНА — без неё два авто-отвечающих бота в чате уйдут в «пинг-понг». `reply_to` при отправке обязателен — он же кладёт реплику в нужную тему форум-группы. Реплика в ЧАТ уходит с `<thought>`, а в АРХИВ групп — только видимая часть (strip_thoughts); перепутаешь — либо стенограмма замусорится мыслями, либо пропадут «Мысли» из чата. Новые места, где бот пишет в группу сам, — не забыть `save_group_message` своей реплики (иначе стенограмма «слепнет») и `note_bot_group_reply` (иначе бот влезет сам сразу после ответа). ИСКЛЮЧЕНИЕ — новостная рассылка (jobs/news.py::send_news_to_chat): она пишет сводку в архив, но `note_bot_group_reply` НЕ зовёт НАМЕРЕННО (решение 2026-07-17) — новость не «реплика в беседе», и пауза после неё мешала бы боту участвовать в обсуждении этой же новости; не «чинить».
- **КОМАНДЫ НЕ ПОПАДАЮТ В СТЕНОГРАММУ (2026-07-24, просьба Максима)** → в `_build_proactive_parts` (services/gemini.py) строки архива, чей текст начинается со слэша, пропускаются целиком: команды адресованы механизму, а не собеседникам. Повод — `/clear`: он стирает личный контекст человека, само сообщение Telegram удаляет сразу, но в архив групп оно попасть успевает (архиватор group=1 работает параллельно с обработчиком команды) — и бот видел стёртое. Фильтр стоит ИМЕННО в сборке стенограммы, а НЕ в `collect_group_message`: архив обязан остаться целым — по нему считается «архив группы за 10 дней» в /stats и берутся запасные имена для /users. Работает и на уже накопленный архив. Триггером команды и так не бывают (`text.startswith("/")` в `consider_message`) — это ВТОРОЙ, независимый заслон, снимать ни один из двух нельзя. Подмена `[фото]`/`[голосовое]`/`[видео]` реальным разбором смотрит на `rows[-1]` и требует пустой текст при вложении — команду она не заденет.
- **Трогаешь «черту» стенограммы (2026-07-20, кнопка «🧹Очистить РАЗГОВОРЫ»)** → метка `proactive_reset_mark` ставится ТОЛЬКО временем самой SQLite (`SELECT CURRENT_TIMESTAMP` в `set_proactive_reset_mark`), а не питоновским временем: `created_at` заполняется SQLite, и при разных форматах сравнение строк перестанет совпадать с хронологическим — черта начнёт скрывать не то. `get_setting`/`set_setting` берут `_lock` САМИ, поэтому звать их только ВНЕ блока `with _lock` (обычный threading.Lock не реентерабельный — вложение повесит бота намертво). Условие «новее черты» живёт в ОДНОМ месте — `get_recent_group_messages`; появится второй читатель стенограммы, добавь условие и ему, иначе бот «вспомнит» забытое. Физическое удаление архива вместо черты НЕ делать (решение Максима 2026-07-20): оно обнулит счётчик «архив группы за 10 дней» в /stats и выбьет из списка /users тех, кто известен боту только по архиву.
- **Меняешь ответы модели** → отправка ТОЛЬКО через `send_formatted`/`convert_md` с entities; `parse_mode` вместе с entities НЕ РАБОТАЕТ (взаимоисключающие).
- **Меняешь MOD_STATS_DAYS (antispam.py)** → он же используется в jobs/cleanup.py::cleanup_loop как срок хранения журнала.
- **Белый список фильтра ссылок** → `LINKFILTER_WHITELIST` в config.py (кортеж доменов; поддомены разрешаются автоматически). Пополняется правкой конфига + рестарт. Он же показывается текстом в панели /mod.
- **Меняешь критерии «проверенного»** → только константы `TRUST_*` в config.py; само правило живёт в ОДНОМ месте — `services/antispam.py::trust_info` (его же показывает /rank). Новые события, влияющие на доверие, — писать в user_dossier через dossier_add_* (database/history.py).
- **Меняешь срок хранения архива групп (10 дней в jobs/cleanup.py::cleanup_loop)** → число «10» зашито текстом в подписи «Архив группы за последние 10 дней» панели /stats (handlers/admin/panel_main.py) и в комментарии `history.py::get_bot_stats` — поправь оба места.
- **Меняешь handle_message (messages.py)** → в начале стоит перехват `kb_test_mode` (режим «🔍 Проверить поиск» панели /rag, зовёт `admin.handle_kb_test_query`) — он должен оставаться ДО проверки тумблера «ответы ИИ», иначе проверка поиска перестанет работать при выключенных ответах.
- **⚡ Рассылка новостей: каждый чат защищён отдельно (2026-07-27)** → в `news_polling_loop` отправка каждому подписчику обёрнута в try/except. Раньше защиты не было, и ОДИН недоступный чат (бота выгнали, группу удалили, отобрали право писать) ронял весь цикл через внешний `except`: остальные подписчики новость не получали, `mark_news_as_sent` не вызывался, `save_pending_news` не доходил — и всё повторялось каждые 10 минут, заново тратя запрос к модели. ⚠️ Отметка «разослано» ставится ДАЖЕ при нулевой доставке — иначе вечный цикл; при нулевой доставке в лог идёт ERROR с числом чатов. Не «оптимизировать» обратно к отметке только после успеха.
