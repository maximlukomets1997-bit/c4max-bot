## 2. Функции бота (проверено по коду)

### 2.1 Публичные команды
- `/start`, `/help` — справка (HTML, панельное сообщение).
- `/clear` — очистка контекста диалога пользователя; подтверждение самоудаляется через 7 сек, после чего в личке у персонала автоматически открывается /adm.
- `/subscribe`, `/unsubscribe` — подписка чата на рассылку новостей.
- `/imagine <описание>` — картинка через Nano Banana (gemini-*-image); лимит 3/день на юзера, админ — безлимит.
- `/rank` — «личное дело»: звание, статистика викторин, остаток лимита картинок, блок «🪪 Служба в гарнизоне» (стаж, сообщений в группах, статус «✅ Проверенный» / «⏳ испытательный срок» / «⚠️ взыскание» — antispam.trust_info), прогресс-бар.
- **Команды `/quiz` НЕТ** — `cmd_quiz` существует в quiz.py, но НЕ зарегистрирован в handlers/__init__.py. Викторина запускается только кнопкой.
- Неизвестная команда → молча удаляется, без ответа.
- В меню Telegram: start, help, imagine, rank, subscribe, clear (без unsubscribe). У админов в личке сверху добавлена /adm.

### 2.2 Админ-команды (только ADMIN_IDS; не-админу — молчаливое удаление команды)
- `/adm` — главная панель-хаб (единственная админ-команда в меню). Только в личке; в группе молча выходит.
- `/stats` — тонкая панель «💬 СТАТИСТИКА» (только личка): 3 строки — обмены «вопрос-ответ» за текущий месяц (из user_token_usage, обнуляется месячным сбросом — см. 2.5), подписчики на новости, архив группы за последние 10 дней; из кнопок только «⬅️ Админ-панель». Бывшая общая панель разделена 2026-07-05 на три: статистика, промпты (`send_prompts_panel`), модели/API (`send_api_panel`) — все три шлются через общий помощник `_send_panel_message` (нарезка >4000 симв., запасной путь без HTML). `get_bot_stats` больше НЕ считает: окна контекста, «сегодня» по диалогам, уникальных пользователей/чатов, «сегодня» по архиву.
- `/mod` — панель модерации (только личка).
- `/users` — панель «👥 Пользователи»: список всех, кого знает бот, и карточка участника (только личка, 2026-07-20). В меню Telegram НЕ добавлена — как /mod, /rag, /stats.
- `/rag` — панель базы знаний (только личка).
- `/unmute` — ТОЛЬКО В ГРУППЕ: ответить командой на сообщение нарушителя. В личке — подсказка.
- `/prompt_set`, `/prompt_add`, `/prompt_reset` — системный промпт (текстом или .txt через Reply).
- `/news_prompt_set`, `/news_prompt_reset` — промпт форматирования новостей.
- `/rag_prompt_set`, `/rag_prompt_reset` — «шапка»-инструкция RAG (текстом или .txt через Reply); reset возвращает ЗАВОДСКУЮ (не «пусто»), с подтверждением. Хранится в settings `rag_instruction`, дефолт `RAG_INSTRUCTION` (config.py). Показывается блоком в панели /prompt.
- `/proactive_prompt_set`, `/proactive_prompt_reset` — инструкция участия в разговоре (режим «Сам в разговор»); зеркала /rag_prompt_* (текстом или .txt через Reply; reset возвращает ЗАВОДСКУЮ, с подтверждением). Хранится в settings `proactive_instruction`, дефолт `PROACTIVE_INSTRUCTION` (config.py). Показывается блоком в панели /prompt.

### 2.3 Кнопки (все проходят через handle_callback_query в handlers/admin/router.py)

### 2.4 Антифлуд (services/antispam.py) — как есть в коде
- По умолчанию ВЫКЛЮЧЕН (`ANTISPAM_ENABLED_DEFAULT = "0"`); включается в /mod. Настройки глобальные на все группы.
- Детектор: ≥N сообщений за окно (дефолт 5 за 5 сек), счётчик в памяти процесса (сбрасывается при рестарте — это нормально).
- Срабатывание: временный мут через `restrict_chat_member` (дефолт 300 сек) → **удаление всего спам-всплеска** → запись в `moderation_log` + **тексты удалённых сообщений в `mute_evidence` (улики) ДО удаления** → сообщение в чат «🛡 X получает мут…» с кнопкой «🔓 Размутить».
- Защищены от мута: ADMIN_IDS, сам бот, админы/владелец Telegram-группы; если статус проверить не удалось — НЕ мутим (безопасный дефолт).
- Пока мут активен, «протёкшие» сообщения нарушителя добиваются поштучно.
- Размут (`unmute()`): восстанавливает ДЕФОЛТНЫЕ права группы (не «всё разрешено»), пишет unmute в журнал с именем админа (параметр admin_name — передают кнопка и /unmute). Вызывается кнопкой и командой /unmute.
- Статистика в /mod: мутов/размутов за 7 дней (`MOD_STATS_DAYS`), последние 5 действий (у размутов приписка «(снял: …)» — из admin_name; старые записи без неё), просмотр улик по кнопке. Хранение 7 дней, чистится cleanup_loop.
- **Альбомы фотографий (2026-07-19):** Telegram шлёт альбом как НЕСКОЛЬКО сообщений с общим `media_group_id` — без поправки альбом из 5 фото мгновенно выбирал порог и человек получал мут ни за что (наступили на этом). Теперь `collect_group_message` передаёт `media_group_id` в `check_and_mute`, а размер всплеска считает `_count_messages`: части одного альбома схлопываются в единицу, РАЗНЫЕ альбомы считаются по отдельности (залп альбомами ловится). В памяти при этом остаются ВСЕ части (удаление спама и улики работают как раньше).
- **Персональные настройки участника (2026-07-20, карточка /users).** Общие пороги перекрываются личными по каждому полю отдельно: `get_thresholds()` — общие (панель /mod), `get_thresholds_for(user_id)` — с учётом личных (её зовёт `check_and_mute` и мут за повторные ссылки). Тумблер «иммунитет» (`antispam_immune`) — автоматика такого человека НЕ мутит вообще: проверяется в самом начале check_and_mute (до регистрации сообщения в счётчике) и отдельно перед мутом за повторные ссылки; на УДАЛЕНИЕ ссылок иммунитет не влияет — для этого свой тумблер `links_allowed` в начале `check_and_delete_links`. Ручного статуса «проверенный» БОЛЬШЕ НЕТ (`trusted_manual` удалён 2026-07-20 вместе с тумблером карточки): `trust_info` считает статус только автоматикой, поля `manual` в её ответе нет; графа `trusted_manual` в `user_settings` осталась в БД мёртвой (как `p_antispam` в staff) — из белого списка `_USER_SETTING_FIELDS` убрана.
- Прогрессивных наказаний НЕТ (MVP — всегда один и тот же мут).
- **Личное дело и статус «проверенный» (2026-07-15):** на каждого участника групп копится вечная запись `user_dossier` (стаж first_seen, msg_count — пишет collect_group_message, mute_count/last_mute_ts — оба пути мута, link_count — фильтр ссылок). Правило доверия ОДНО — `antispam.trust_info(user_id)`: стаж ≥ `TRUST_MIN_DAYS`(7) И сообщений ≥ `TRUST_MIN_MESSAGES`(100) И мутов нет (или последний старше `TRUST_FORGIVE_DAYS`(30) — прощение). ⚠️ БОНУСА К ПОРОГУ АНТИФЛУДА БОЛЬШЕ НЕТ: `TRUST_EXTRA_MESSAGES` удалена 2026-07-20 (решение Максима), проверенный мутится наравне со всеми; статус чисто информационный — его показывают /rank, карточка /users и справка об авторе в проактивном режиме, `check_and_mute` его не читает. /rank показывает блок «🪪 Служба в гарнизоне» (стаж, сообщения, статус) через тот же trust_info. Стаж копится с момента внедрения (дата вступления в группу у Telegram не запрашивается).
- **Фильтр ссылок (2026-07-14, `check_and_delete_links`):** отдельный тумблер «🔗» в /mod (ключ `linkfilter_enabled`, дефолт ВЫКЛ, НЕ зависит от тумблера антиспама). Ловит entity url/text_link в тексте И подписи к фото (разбор только через `parse_entities` — смещения UTF-16!). Белый список `LINKFILTER_WHITELIST` (config.py, дефолт wtmobile.com; поддомены проходят, подделки вида wtmobile.com.evil.ru — нет). Защищённые (`_is_protected`) не трогаются. Действие: удалить сообщение → журнал `moderation_log` (action="linkdel") + улика в `mute_evidence` → предупреждение в чат (самоудаляется 15 сек). За `LINKFILTER_MUTE_COUNT`(3) удалений за `LINKFILTER_WINDOW_SEC`(час) — временный мут обычной длительности (ключ antispam_mute_sec) с кнопкой размута; счётчик повторов `_link_strikes` в памяти. Вызов — из collect_group_message ПОСЛЕ антиспама и только если тот не замутил. Ограничение: видит только текст/фото (фильтр group=1), обходы «точка ком» не ловит.
- **Уведомление модераторов об автоматическом муте (2026-07-20):** после мута за флуд И после мута за повторные ссылки `_notify_moderators_mute` шлёт в личку МОДЕРАТОРАМ (только тем, у кого есть право `mod` — остальным кнопка всё равно не нажмётся) сообщение с названием группы, причиной и кнопкой «🔓 Размутить». ВЛАДЕЛЬЦАМ намеренно НЕ шлётся: у них есть панель /mod с полным журналом (захочешь — одна строка в функции). Ручные муты из карточки уведомления не порождают — их сделал человек, и они видны в журнале персонала. Функция «тихая», как вся antispam.py.
- **Иерархия персонала (2026-07-20):** `_is_protected` не даёт автоматике мутить ВЕСЬ персонал (`roles.is_staff` — владельцы и модераторы). У ручных действий своя охрана `_manual_guard(bot, target_id, actor_id)`: владелец может ко всем, модератор — только к обычным участникам (ни к владельцу, ни к другому модератору, ни к себе; правило одно — `roles.can_act_on`). Все ручные действия принимают `actor_id` — не забыть передать его из панели, иначе охрана вернётся к старому правилу «персонал не трогаем» и модератор сможет мутить модератора. Потолок срока мута для модератора — `config.MODERATOR_MAX_MUTE_SEC`, проверяется ДВАЖДЫ: длинные сроки не показываются на кнопках И отбиваются при выполнении (нажатие старой кнопки не должно обходить лимит).
- **Ручные действия админа (2026-07-20, кнопки карточки /users):** `mute_user` (мут на выбранный срок), `unmute` (был), `kick_user` (в Telegram это бан + немедленное снятие — иначе человек не сможет вернуться), `ban_user`, `unban_user`. Возвращают ПУСТУЮ строку при успехе или текст ошибки Telegram (панель показывает его во всплывающем окне) — в отличие от автоматики, которая всё глушит молча. Проверку `_is_protected` они НЕ применяют (админ группы вполне может быть целью), вместо неё `_manual_guard`: нельзя трогать админов бота из ADMIN_IDS и самого бота. Всё остальное разрешает или запрещает Telegram.
- **Типы записей журнала модерации:** `mute` (автоматика), `mute_adm` (ручной мут), `linkdel`, `unmute`, `kick`, `ban`, `unban`. Панель /mod перечисляет их ЯВНО (словарь `icons` в `_build_mod_panel_text_and_keyboard`): раньше «всё остальное» рисовалось как размут, и с приходом ручных действий журнал начал бы врать. Улики (`mute_evidence`) есть только у `mute` и `linkdel` — кнопка «📜» показывается только им. Графа `admin_name` теперь показывается у ВСЕХ ручных действий («снял:» у размута/разбана, «админ:» у остальных).
- Вся модерация «тихая»: любое исключение глушится, бот не падает.

### 2.5 Автоматическое поведение
- **ИИ-ответы:** личка — на всё; группа — только при @упоминании (в тексте или подписи к фото/видео) или Reply на сообщение бота. Фото — анализ (если активная модель без поля vision — DeepSeek/Qwen — фото ей не отправляется: vision-reroute сразу на цепочку Gemini, без уведомления админам), голос/аудио — через `AUDIO_FALLBACK_CHAIN`, ВИДЕО (2026-07-24) — через `VIDEO_FALLBACK_CHAIN` с проверкой поля `"video"`; подпись к видео уходит модели как вопрос, статус «🎬 Смотрю видео…» удаляется после ответа. Видео больше 20 МБ (`VIDEO_MAX_BYTES`) бот не скачивает — Telegram столько и не отдаёт — и честно отвечает, что ролик великоват. Статус «печатает…» висит всё время генерации.
- **RAG при ответах:** каждый текстовый запрос (и подпись к фото) уходит в гибридный поиск (один дешёвый вызов эмбеддинга, кэш повторов на 128 запросов); статьи, прошедшие отбор (балл = смысл + слова, «пик против полки» — см. services/rag.py), попадают в системный промпт ЦЕЛИКОМ под «шапкой»-инструкцией (`get_rag_instruction`: своя из settings `rag_instruction` или заводская `RAG_INSTRUCTION`; правится из /prompt командами /rag_prompt_*), формат каждой статьи «=== РАЗДЕЛ: … ===». Работает НЕЗАВИСИМО от тумблера «PROMPT ВЫКЛ» (решение 2026-07-05), но подчиняется ОБЩЕМУ тумблеру «📖 База знаний» панели /rag (settings `rag_enabled`, с 2026-07-27 — один на весь бот; проверка внутри `rag.retrieve_relevant_context`, поэтому её слушаются все пути сразу: личка, группы, «Сам в разговор»). Голосовые RAG не используют (аудио уходит модели напрямую).
- **Добор базы знаний (2026-07-19, jobs.py::rag_catchup_loop):** раз в час проверка полноты векторного индекса (`rag.index_lag()` — сравнение файлов и mtime, БЕЗ запросов к Google). Индекс полный → тишина (ни лога, ни запросов). Неполный (сбой квоты Google) → обычная синхронизация недостающего под той же защёлкой `kb_rebuild_running` (идущую ручную пересборку не трогает — пропускает свой час). Уведомления админам в личку ТОЛЬКО на границах инцидента: одно «⚠️ база неполная X из Y» при первой неудаче добора, одно «✅ снова полная» при выздоровлении; между ними — строки в логе раз в час. Первая проверка через час после старта (стартовую синхронизацию делает main.py). Сообщения не регистрируются в гигиене панелей — остаются в чате как история.
- **Архив групп (`collect_group_message`, group=1):** пишет сообщения групп в `group_messages` и зовёт антиспам. Фильтр — `TEXT|PHOTO|VOICE|AUDIO|VIDEO`: голосовые и аудио попадают с 2026-07-21 (графа `has_voice`), видео с 2026-07-24 (`has_video`). СТИКЕРЫ, КРУЖОЧКИ (VIDEO_NOTE) и ГИФКИ (ANIMATION) не попадают — их не видит и антиспам. С 2026-07-16 в архив пишутся и СВОИ ответы бота в группах (прямые — через `_archive_bot_group_reply`, проактивные — из `_run_proactive`): собственные сообщения апдейтами не приходят, а стенограмма «Сам в разговор» должна видеть, что бот уже говорил.
- **«Сам в разговор» (2026-07-16, services/proactive.py):** тумблер `proactive_enabled` в панели промптов, дефолт ВЫКЛ. На каждое сообщение группы (в конце collect_group_message, только если не было ни мута, ни удаления ссылки) — дешёвые фильтры: защёлка «в полёте», не бот (защита от петли бот-бот), не команда, не игнор из карточки (`ai_ignored`), не прямое обращение, тумблер, порог новых сообщений (`proactive_min_msgs`). СУДЬЯ УДАЛЁН 2026-07-20: быстрые модели без мышления плохо следуют инструкциям. Прошло всё → отдельной задачей ОДИН запрос `ask_group_proactive` (активная думающая модель И решает, И пишет): стенограмма последних N сообщений («Ты: …» — свои; N — регулятор «📜 контекст» панели, ключ `proactive_context_msgs`, дефолт `PROACTIVE_CONTEXT_MSGS`=25) + характер + RAG по триггеру + инструкция (`get_proactive_instruction`, включает блок рук — модель видит его всегда); модель пишет реплику ИЛИ слово «ПРОПУСК» (маркер ищется в видимой части, без `<thought>`). Запрос идёт через АКТИВНУЮ модель с обычной цепочкой подстраховки. Реплика уходит В ЧАТ С МЫСЛЯМИ (свёрнутый блок). Стенограмму можно обнулить кнопкой «🧹Очистить РАЗГОВОРЫ».
- **Новости:** каждые 10 мин скрейпинг wtmobile.com/ru → форматирование моделью (промпт `news_system_prompt`) → рассылка подписчикам альбомом (главная картинка + 1 карточка ТТХ; текст ≤1024 — подписью, иначе отдельно) → исходный текст в `knowledge/pending/`. - **Викторина:** после ответа любого участника через 2.5 сек автоматически следующий вопрос (ровно один раз на опрос; пауза — отложенной задачей, бот в это время не стоит); каждый опрос автоудаляется через 60 сек; повышение звания → поздравление в ЛС.
- **Очередь апдейтов (2026-07-13):** апдейты обрабатываются по одному (concurrent_updates НЕ включён — вариант А аудита отложен), НО пять долгих хендлеров (текст/фото/голос/видео → ИИ и /imagine) зарегистрированы с `block=False` и выполняются отдельными задачами — долгий ответ нейросети одному пользователю больше не морозит остальных, панели, антиспам и архив групп. Побочный эффект: два вопроса от одного человека подряд могут обрабатываться параллельно (ответы придут в произвольном порядке) — принято как допустимое.
- **Гигиена сообщений:** новое «панельное» сообщение бота удаляет предыдущее в том же чате (`bot_sent_messages`, переживает рестарт); команды пользователей удаляются; служебные подтверждения самоудаляются через 15–30 сек.
- **Лог команд (2026-07-13):** каждая входящая команда пишется в лог строкой «⌨️ Команда: … | от … | личка/чат» центральным регистратором `log_incoming_command` (handlers/commands.py, group=-1) — до основных обработчиков, текст длиннее 100 символов обрезается. Старые точечные строки лога команд, «скрытые по просьбе» в 2026-07, НЕ раскомментировывать — их заменяет регистратор. Выключается одной строкой регистрации в handlers/__init__.py.

- **Недельный отчёт о расходах (2026-07-25, тот же `jobs.py::daily_report_loop`):** каждый ПОНЕДЕЛЬНИК в 00:00 по Киеву ВЛАДЕЛЬЦУ в личку следом за суточным уходит ВТОРОЕ сообщение «📅 РАСХОД ЗА НЕДЕЛЮ» за пн–вс — те же блоки и подписи, что у суточного, плюс строка «📈 В среднем в день: вызовов N · ≈$X» в самом низу (решение Максима). Считается СУММОЙ уже посчитанных суток: каждый суточный отчёт кладёт свои цифры в копилку (`weekly_report_acc`), в понедельник копилка становится отчётом и обнуляется — прямая разница снимков за 7 дней врала бы на неделе с месячным сбросом (см. раздел 3). Условия отправки два: наступил понедельник ЛИБО с начала копилки прошло ≥7 суток (страховка на проспанный понедельник); проверка стоит ПОСЛЕ суточного отчёта, чтобы воскресные сутки успели попасть в копилку. Суток в отчёте меньше или больше семи (бот не работал) — честная подпись «дней: N» и предупреждение, среднее делится на реальное число суток. Первый отчёт после внедрения придёт в ближайший понедельник за неполную неделю. Сообщение, как и суточное, идёт БЕЗ гигиены панелей. Кнопка «📅 Отчёт за неделю» в панели «📡 Настройки API» показывает СОХРАНЁННЫЙ текст (settings `weekly_report_last_text`) плюс живой хвост «с начала недели … : вызовов N · ≈$X».
- **💾 Ночная копия базы (2026-07-31, `jobs.py::nightly_backup`, просьба Максима):** раз в сутки в 00:00 по Киеву бот делает копию `history.db` и отправляет её ВЛАДЕЛЬЦУ в личку СЛЕДОМ ЗА суточным отчётом о расходах. Повод: копий у базы не было вообще, а в ней всё, чего нет на GitHub, — промпты, настройки, остатки счетов и квот, вечные личные дела, звания, журналы. Копий теперь ДВЕ, и они закрывают разные беды: `BACKUP_KEEP`(7) штук на сервере в `backups/` (откат за секунды при «стёр не то») и файл в Телеграме у владельца (единственное, что переживает смерть сервера). Частоту выбрал Максим из трёх вариантов (ночь / неделя / только по кнопке) — ночь. ⚠️ ТУМБЛЕРА У НОЧНОЙ ОТПРАВКИ НЕТ намеренно: копия, которую можно случайно выключить и забыть, — это отсутствие копии. ⚠️ ЖИВЁТ ВНУТРИ ЦИКЛА СУТОЧНОГО ОТЧЁТА, а не своим циклом: два цикла, проснувшихся в одну полночь, о порядке «копия следом за отчётом» не договорятся, а этот уже умеет просыпаться к полуночи по Киеву кусками не больше часа и догонять пропущенное. Своим `try` — сорвавшаяся копия не мешает отчётам и наоборот. ⚠️ Условие отправки СВОЁ (`backup.due_today()`, метка settings `backup_last_date`), а не отчётное: отчёт мог не уйти вовсе, а копия нужна в любом случае. ⚠️ Метка ставится ТОЛЬКО после удачной доставки — не дошло, попробуем через час, а не махнём рукой до завтра (то же правило, что у тревоги сторожа). ⚠️ Снимок берётся штатным `Connection.backup` (`history.backup_to`), а НЕ копированием файла: база в режиме WAL, простое копирование даёт отставшую, а то и битую копию. Работа с диском уходит в отдельный поток — на её время бот не перестаёт отвечать людям.
- **🐕 Сторож: уведомление о том, что бот перестал отвечать (2026-07-27, `jobs.py::watchdog_loop` + `watchdog_local.py`):** бот раз в МИНУТУ отмечается у ВНЕШНЕГО сторожа (healthchecks.io, адрес в `.env` → `WATCHDOG_URL`) и пишет местную метку `bot.alive`. Перед КАЖДОЙ отметкой спрашивает `get_me` у Telegram: не ответил — не отмечается нигде. Отметки прекратились дольше Grace Time (у Максима Period 1 мин / Grace 2 мин) → healthchecks.io САМ пишет владельцу в Telegram (@HealthchecksBot). Плюс «крик умирающего»: при штатной остановке бот сам шлёт `/fail` и тревога приходит за секунды (`main.py::_cry_for_help`; кнопка перезапуска крик не шлёт). ⛔ МЕСТНЫЙ СТОРОЖ ВЫКЛЮЧЕН 2026-07-27 вечером (решение Максима: сообщения healthchecks.io в Телеграм и на Gmail достаточно, местный их дублировал) — задание планировщика «C4_Max Bot Watchdog» в состоянии Disabled, `watchdog_local.py` не запускается ничем, ДВУХ сообщений от бота («🔴 БОТ НЕ ОТВЕЧАЕТ» и «✅ Бот снова работает») БОЛЬШЕ НЕТ. Код цел, включается обратно одной командой (см. таблицу файлов). Когда он включён: задание раз в минуту запускает `watchdog_local.py` (три проверки за запуск, шаг 20 сек): процесс из `bot.pid` жив И метка `bot.alive` свежее 3 минут? Нет — и так ДВА раза подряд — сообщение владельцу напрямую через Bot API. За происшествие ровно два сообщения (тревога + восстановление). ЧТО ЛОВИТСЯ СЕЙЧАС (только внешним): выключенный компьютер, пропавший интернет, упавший, закрытый или зависший бот — всё за ~3 мин; ШТАТНАЯ остановка — секунды (крик). С включённым местным было бы быстрее: упавший бот или закрытое окно ~40 сек, зависший ~3.5 мин. ⚠️ Пока интернета нет, отправить не может НИКТО: уведомление уходит, когда связь вернулась (проверено настоящей аварией 2026-07-27). ЧТО НЕ ЛОВИТСЯ: одновременная пропажа интернета у компьютера И у телефона (сообщение придёт, когда телефон вернётся в сеть) и падение самого healthchecks.io (тогда возможна ложная тревога). РЕШЕНИЕ МАКСИМА 2026-07-27: при РУЧНОЙ остановке бота тревогу НЕ глушить — «пусть присылает», паузу через Management API не заводили. Кнопка «🔄 ПЕРЕЗАПУСТИТЬ БОТА» тревоги не поднимает: перезапуск занимает секунды, а обоим сторожам нужны минуты.
- **Месячный сброс статистики API (2026-07-09):** `jobs.py::_monthly_stats_reset` — раз в сутки (из cleanup_loop) сверяет текущий месяц ПО КИЕВУ с меткой settings `stats_reset_month` («ГГГГ-ММ»). Месяц сменился → каждому админу в личку «📊 Итоги месяца» (расходы DeepSeek/Qwen/картинок + вызовы по моделям + обмены «вопрос-ответ»; сообщение НЕ регистрируется в гигиене панелей — остаётся в чате как история), затем обнуление: таблица api_calls очищается (`hist.clear_api_calls`), ключи `qwen_cost_usd`/`image_cost_usd` = 0 (⚠️ `xiaomi_cost_usd` с 2026-07-25 тоже НЕ обнуляется — вечный счётчик, сверяется с кабинетом Xiaomi, в «Итогах месяца» помечен «за всё время»; `deepseek_cost_usd` с 2026-07-21 НЕ обнуляется — вечный счётчик, сверяется с кабинетом DeepSeek; в «Итогах месяца» его строка помечена «за всё время»), обмены «вопрос-ответ» обнуляются (`hist.clear_user_token_usage`, с 2026-07-09 — поэтому в /stats подпись «за этот месяц»). Сброс НЕ ровно в полночь: при первой суточной проверке в новом месяце (бот мог быть выключен 1-го — тогда при первом запуске). Пустая метка (первый запуск) → просто ставится, без сброса. НЕ сбрасываются: лимиты картинок, статистика викторин/званий, промпты, настройки.

## 3. Зависимости: «меняешь X — проверь Y»

- **Добавил модель в `AVAILABLE_MODELS` (config.py)** → кнопка в панели «📡 Настройки API» НЕ появится сама! Раскладка кнопок — списки `_MODEL_BUTTON_ROWS` / `_IMAGE_BUTTON_ROW` в handlers/admin/panel_main.py, собраны ВРУЧНУЮ по ключам моделей. Меняешь состав моделей — правь обе точки. Группировка вызовов в тексте панели идёт по полю `provider` — новые провайдеры (не gemini/qwen/deepseek) в разбивку не попадут. И НЕ забудь поле `vision`: без него (или с False) модель не будет получать фото — их перехватит vision-reroute (services/gemini.py) и отдаст цепочке Gemini.
- **Значки провайдеров в логах и панели API (2026-07-19)** → заданы В ОДНОМ месте: `PROVIDER_ICONS` в config.py (+ запасной `PROVIDER_ICON_FALLBACK` 🤖 и `RAG_ICON` 📚). Читают их services/gemini.py (помощник `_icon_of`, строки «Запрос к модели» / «Ответ от …», текст и аудио), services/rag.py (строки поиска) и handlers/admin/panel_main.py (заголовки блоков панели). Новый провайдер → добавь значок туда, иначе в логах он пойдёт под 🤖. Значок в строке лога брать ПО МОДЕЛИ ЭТОЙ СТРОКИ (`chain[0]`, `model_name`), НЕ по активной — иначе уход на запасную модель другого провайдера станет незаметным. `_icon_of` смотрит в AVAILABLE_MODELS напрямую, а не через `_provider_of` (тот незнакомой модели отвечает «gemini» — значок вышел бы ложным).
- **Новая команда** → обязательно зарегистрировать в `handlers/__init__.py::setup_handlers`, иначе `handle_unknown_command` будет МОЛЧА УДАЛЯТЬ её без ответа (выглядит как «бот игнорирует»). Плюс решить: добавлять ли в меню (main.py::post_init).
- **Объявление «БАН» при выключении режима «Сам в разговор» (2026-07-24, просьба Максима)** → текст `PROACTIVE_OFF_ANNOUNCE` в config.py продиктован им ДОСЛОВНО, формулировку не править и не «улучшать»; обратного объявления («бан снят») он НЕ хочет — включение просто удаляет сообщение. Механика: `_announce_proactive_off` / `_remove_proactive_off_announce` в panel_prompts.py, координаты отправленных сообщений — список пар `[chat_id, message_id]` в JSON, ключ settings `PROACTIVE_OFF_MSGS_KEY`. Три правила, которые нельзя «чинить»: (1) объявление НЕ регистрируется в гигиене панелей (`register_and_clean_bot_message`) — иначе его затрёт первая же панель, а висеть оно должно до включения режима; (2) координаты только в БД, не в памяти — иначе перезапуск бота, и удалять нечем, объявление зависнет навсегда; (3) сбой отправки/удаления в одной группе молча пропускается и НЕ ломает переключение тумблера (сама ветка `toggle` тоже обёрнута в try). Рассылка идёт по `get_known_chats()` — новая группа подхватится сама, как только бот увидит там сообщение. ⚠️ Telegram не даёт ботам удалять сообщения старше 48 часов: режим, выключенный дольше двух суток назад, оставит объявление в группе навсегда — удалять руками.
- **⚠️ ЗАШИТЫЕ ФРАЗЫ-ИНСТРУКЦИИ К МЕДИА УДАЛЕНЫ (2026-07-24, решение Максима)** → модели уходит ТОЛЬКО файл, без единого слова от бота. Удалены все пять: «Кратко опиши, что на этом фото…» (`_proactive_describe_image`), «Расшифруй это голосовое сообщение…» (`_proactive_transcribe_audio`), «Опиши КРАТКО… что происходит на этом видео» (`_proactive_describe_video`), «Ответь на это голосовое сообщение пользователя.» (`ask_gemini_audio`) и заготовка для видео без подписи (`ask_gemini_video`). Повод: Максим не хочет, чтобы бот подсказывал моделям формулировки от себя (претензия была именно к тому, что фразы сочинены и зашиты без его ведома). НЕ возвращать ни одну из них по своей инициативе — только по прямой просьбе. Добавляя новый вид медиа, фразу-инструкцию тоже НЕ сочинять: шли голый файл. ⚠️ ИЗВЕСТНОЕ ПОСЛЕДСТВИЕ, принято Максимом осознанно («оставить как есть»): в ПРЯМЫХ ответах стало лучше (характер бота из `systemInstruction` ведёт модель сам — проверено живым тестом, ответы в образе и по-русски), а в ПРОАКТИВНОМ разборе характера нет, и модель отвечает как хочет — на живом тесте описания фото и видео пришли ПО-АНГЛИЙСКИ, списками и с таймкодами, а вместо расшифровки голосового модель начала сама отвечать на вопрос. Всё это попадает в стенограмму беседы. Увидишь английский/списки в стенограмме — это не баг, а следствие этого решения.
- **Трогаешь ВИДЕО (2026-07-24)** → четыре правила. (1) Потолок `VIDEO_MAX_BYTES` = 20 МБ — это предел Telegram Bot API на скачивание файла ботом, обойти его нельзя; проверять `video.file_size` ДО `get_file()`, иначе тянем впустую, а человек не понимает, почему бот молчит. `file_size` иногда не приходит — тогда пробуем скачать, падение ловит общий `except`. (2) Обработчик зарегистрирован на `filters.VIDEO` и ТОЛЬКО на него: кружочки (`VIDEO_NOTE`) и гифки (`ANIMATION`) Максим обрабатывать не захотел — не добавлять «до кучи». (3) Цепочка `VIDEO_FALLBACK_CHAIN` задаёт ПОРЯДОК, а право на видео проверяется полем `"video"` через `_supports_video` — модель без поля в запрос не попадёт даже из цепочки. Новая модель, принимающая видео → поставь ей `"video": True` в config, иначе видео ей не отправится. (4) В проактивном режиме свой, БОЛЕЕ НИЗКИЙ потолок `PROACTIVE_VIDEO_MAX_BYTES` = 8 МБ: прямое обращение к боту — просьба человека, а проактив срабатывает на КАЖДОЕ видео в группе. Ролик крупнее остаётся в стенограмме пометкой «[видео]» без описания. Размер неизвестен → в проактиве видео НЕ разбирается (лучше пропустить, чем вслепую тянуть 20 МБ на каждой проверке).
- **Новый ДОЛГИЙ хендлер (сетевые вызовы, run_in_executor)** → регистрировать с `block=False` (как handle_message/handle_photo/handle_voice/handle_video/cmd_imagine), иначе он заморозит всю очередь апдейтов на время работы. И наоборот: хендлеры, чувствительные к порядку (панели, антиспам, настройки), оставлять блокирующими. Внутри block=False-хендлера проверки «проверил → списал» (как лимит картинок) должны идти БЕЗ await между ними, иначе появится гонка.
- **Лимит картинок (/imagine)** → списывается ДО генерации (`register_image_call` сразу после проверки остатка, без await между ними), при неудаче возвращается (`unregister_image_call`). НЕ переносить списание «после генерации» — залп команд /imagine обойдёт лимит (хендлер неблокирующий).
- **Чужой текст в HTML-панелях (имена пользователей, заголовки статей)** → ВСЕГДА через `html.escape(...)`: символ «<» в имени/заголовке ломает отправку панели (наступили на этом в /mod и журнале /rag, исправлено 2026-07-13; также /rank и поздравление о звании).
- **Новая inline-кнопка** → её callback обязан обрабатываться в `handlers/admin/router.py::handle_callback_query` (единый роутер). Кнопки для ВСЕХ пользователей добавлять ДО гейта прав (как quiz_start). Кнопку для персонала — вписать в `_CALLBACK_RULES` (services/roles.py) с нужным правом, иначе она останется доступна ТОЛЬКО владельцу (запрет по умолчанию; это не баг, а защита — но модератор пожалуется, что кнопка не работает). С 2026-07-20 та же строка таблицы решает и ВИДИМОСТЬ: панели персонала прогоняются через `_filter_keyboard` — отдельного «списка что показывать» больше нет и заводить его не надо.
- **Прячешь кнопку от модератора (2026-07-20)** → правь ТОЛЬКО таблицу `_CALLBACK_RULES` / `_ACTION_PERMS` / `_SETTING_PERMS` в services/roles.py. Не возвращать проверки `if roles.can(viewer, …)` в сборку клавиатур: тогда «видит» и «может» снова разъедутся, и однажды кнопка нарисуется, но не нажмётся (или наоборот). Контекстные проверки — другое дело и остаются на месте: ряд картинок не рисуется админам бота (у них безлимит), кнопки роли — цели-владельцу, «↩️ Сбросить всё персональное» — когда сбрасывать нечего.
- **Кнопка-заглушка со значением (`…:noop`)** → у регулятора ➖/значение/➕ средняя кнопка обязана иметь callback, оканчивающийся на `noop`: по этому окончанию `_filter_keyboard` понимает, что ряд без ➖ и ➕ показывать незачем. Назовёшь иначе — у модератора останется висеть одинокая полоса с числом.
- **Названия и подписи прав в roles.PERMS** → их читает владелец на экране «⚙️Настройки Прав Модератора», решая, что выдавать. `title` права `mod` — «🛡DDoS-Guard» (2026-07-20, переименовано из «🛡 Модерация» вслед за разделом; код права, графа `p_mod` и callback'и НЕ менялись — выданные права не слетают). Название права идёт И в текст экрана, И на кнопку-галочку: правится в ОДНОМ месте, в PERMS. ## 4. Хрупкие места (легко сломать по незнанию)

- **entities vs parse_mode** — указать оба = ошибка отправки. Модельные ответы — entities, свои тексты панелей — HTML parse_mode. Не смешивать.
- **callback_data ≤ 64 байта** — имена файлов БЗ туда не влезают, поэтому токены в `bot_data["kb_file_map"]`. После рестарта карта пуста → старые кнопки «протухают» (обработано: панель открывается заново). Любые новые кнопки с длинными данными — тот же паттерн.
- **settings — только строки.** `get_setting` возвращает str; забыть int() = тихий баг сравнения.
- **⚡ Соединение с базой одно на процесс (2026-07-27)** — и это меняет цену ошибки. Раньше забытый `commit()` или упавшая на середине функция просто теряли свою запись вместе с соединением; теперь недописанная транзакция остаётся в общем соединении. Страховка есть (`_DbLock` откатывает при вылетевшем исключении), но она НЕ спасает от двух вещей: забытого `commit()` (запись уедет в чужую транзакцию) и исключения, проглоченного ВНУТРИ блока замка (там нужен свой `rollback()`). Ещё: `close_db()` в `main.py::post_shutdown` стоит ПОСЛЕ остановки фоновых задач — перенесёшь выше, и задачи, ещё живые, полезут в закрытую базу. Само `close_db()` безопасно: после него первое же обращение откроет базу заново.
- **⚡ Сетевые сессии живут по потокам (2026-07-27)** — `services.http.session()` отдаёт разные объекты в разных потоках, и это НЕ баг. Не «оптимизировать» до одной общей сессии: запросы к моделям идут из рабочих потоков (`run_in_executor`), а `requests.Session` потокобезопасности не обещает. И не хранить сессию в переменной модуля (`_S = session()` на уровне файла) — она достанется одному потоку, а пользоваться ею начнут все.
- **`inline_keyboard` у InlineKeyboardMarkup — кортеж**: складывать клавиатуры только через `list(...) + list(...)`, иначе TypeError.
- **Групповой фильтр group=1 — TEXT|PHOTO|VOICE|AUDIO|VIDEO (с 2026-07-24)**: антиспам НЕ видит стикеры, кружочки и гифки. Расширяя фильтр — проверь, что collect_group_message переживёт новые типы.
- **Панельные админ-команды в группе молча выходят** — это не баг, а защита; не «чинить».
- **`_is_protected` при ошибке проверки статуса возвращает True (не мутить)** — не «оптимизировать» в обратную сторону.
- **bot.pid** — вторая копия убивает первую через taskkill. Запуск двух ботов для «теста» невозможен без IS_DOCKER=true. На Linux/хостинге файл вообще не создаётся: там IS_DOCKER=true по умолчанию (см. раздел 3).
- **Лимит Telegram ~15 сек на ответ callback** — долгие операции (пересборка RAG) идут через run_in_executor, а `_kb_popup` имеет запасной путь. Новые долгие кнопки делать так же.
- **Всплывающее окно кнопки (query.answer show_alert) — максимум 200 символов.** Длиннее → BadRequest Message_too_long, окно НЕ показывается, кнопка выглядит «мёртвой» (наступили 2026-07-05 на подсказке «Проверить поиск»). Вдобавок в PTB BadRequest наследуется от NetworkError, поэтому `main._error_handler` пишет такие ошибки в лог как «Временная сетевая ошибка» — не верь этой формулировке, проверяй текст ошибки.
- **Перерисовка клавиатуры «в то же самое» = ошибка Telegram** «Message is not modified»: кнопка-тумблер, нажатая в уже установленное положение, роняет предупреждение в лог и выглядит мёртвой. Перед `edit_message_reply_markup`/`edit_message_text` сравнивай новое состояние с текущим и молча выходи, если ничего не изменилось (сделано на кнопках выбора моделей 2026-07-19).
- **Тексты панелей ≤4096 символов** — превью промптов обрезаются до 600 (`PROMPT_PREVIEW_MAX`); сворачиваемая цитата ВСЁ РАВНО считается в лимит.
- **Надписи кнопок-тумблеров = ТОЛЬКО через `_onoff(состояние)` из handlers/admin/common.py** (стандарт 2026-07-20, решение Максима). Кнопка показывает ТЕКУЩЕЕ СОСТОЯНИЕ — «🟢ВКЛ» / «🔴ВЫКЛ», а НЕ действие: надписи вида «🔴 Выключить антиспам» (означало «сейчас включён», красный кружок при работающей защите) читались наоборот и все переделаны. В ТЕКСТЕ панелей остаются полные слова — «🟢 ВКЛЮЧЁН» / «🔴 ВЫКЛЮЧЕН», их `_onoff` не касается. Новый тумблер — брать метку отсюда, свою надпись не сочинять. ⚠️ ПЕРЕВЁРНУТОЙ осталась ОДНА настройка: `admin_no_prompt_<id>` держит «1» при ВЫКЛЮЧЕННОМ промпте — перед передачей в `_onoff` значение инвертируется (`!= "1"`). Второй перевёртыш, `admin_no_rag_<id>`, умер 2026-07-27 вместе с персональным тумблером RAG: живой ключ `rag_enabled` хранится ПРЯМО, как `thoughts_enabled` и `proactive_enabled`. Новые тумблеры заводить только с прямой семантикой — инверсия каждый раз стоила ошибки. ⚠️ Докстринг `_onoff` в `common.py` всё ещё поминает `admin_no_rag_<id>` — устарел, коду не мешает. (Тумблер «✅ Проверенный» с тремя состояниями удалён 2026-07-20 — все живые тумблеры теперь двухпозиционные и обязаны идти через `_onoff`.) Проверять правку тумблера прогоном обоих положений (сборка панели + печать надписи), а не глазами — на инверсии ошибиться проще всего.
- **Разделитель панелей = 27 символов `─` (U+2500)** — единый стандарт для ВСЕХ панелей (2026-07-06). Новые панели/строки-разделители делать ровно 27. НЕ путать с комментариями-разделителями в коде (45/47 символов `─` в шапках функций — они пользователю не видны, их не трогать).
- **Логи** — новый файл `logs/«дд.мм чч-мм».log` на каждый запуск; логи прошлых запусков не удаляются, а склеиваются в `logs/archive.log` (последние 7 сессий, `ARCHIVE_SESSIONS_TO_KEEP`). **Команды, которые нужны чаще всего** (выполняются с ПК Максима):

```
ssh c4max "systemctl status c4max-bot"     # жив ли
ssh c4max "journalctl -u c4max-bot -n 50"  # свежие строки лога
ssh c4max "systemctl restart c4max-bot"    # перезапустить
ssh c4max c4max-update                     # забрать код с GitHub и перезапустить
```

**Чем сервер отличается от домашнего компьютера — важное для правок кода:**

- `IS_DOCKER` там **True** (считается автоматически: не Windows → управляемая
  среда). Отсюда: `bot.pid` не пишется, старые копии не убиваются, а кнопка
  «🔄 ПЕРЕЗАПУСТИТЬ БОТА» просто завершает процесс с кодом 1 — поднимает его
  systemd. Уберёшь `Restart=always` из службы — кнопка станет кнопкой
  выключения.
- Логи идут **в journalctl**, а не только в файлы `logs/`. Файлы тоже пишутся,
  их отдаёт кнопка «📜 Логи бота».
- **Windows-приспособления там не работают и не нужны:** `watchdog_local.py`
  (задание планировщика, ctypes), новое окно консоли при перезапуске,
  `taskkill` по `bot.pid`. Код это уже учитывает — не «чинить».
- Снаружи открыт **только SSH** (ufw), вход по паролю выключен, подбор паролей
  банит `fail2ban`. Откроешь боту веб-порт — не забудь `ufw allow`.
- `.env` и `history.db` лежат на сервере и **через GitHub не ездят никогда**.
  Меняешь ключ — меняй на сервере отдельно.
- Папка `backups/` (ночные копии базы, 2026-07-31) — там же и тоже мимо
  GitHub: это те же живые данные. Копия за прошлую ночь есть и у Максима
  в личке — при переезде на другой сервер восстанавливаться проще оттуда.
- Файлы, которые бот перезаписывает сам, **не должны быть в репозитории**
  (см. `knowledge/knowledge_base_vectors.json` в разделе 3) — иначе обновление
  упрётся в «файл изменён и там, и тут».
- Управление самим сервером (стоп/старт/перезагрузка, VNC, переустановка) —
  в личном кабинете s-host. **«Стоп» + «Старт» безопасны:** бот поднимется сам,
  ничего не теряется; сторож healthchecks.io пришлёт тревогу «не отвечает» и
  потом «снова работает» — это ожидаемо, он не отличает выключение от аварии.
